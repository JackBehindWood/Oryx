# Python API

## Python API Design

Python should not simply mirror C++.

A Python user should be able to work at a higher conceptual level.

For example:

```python
experiment = Experiment(
    game=game,
    strategies=[random_strategy, mcts_strategy],
    games=10_000,
)

results = experiment.run()
```

This is illustrative rather than a proposed final API.

The actual API should be designed after the C++ core abstractions are clearer.

## Bindings

pybind11 is the current intended binding technology.

The binding layer should act as an API boundary rather than exposing every internal C++ type.

Internal C++ implementation details should remain internal where possible.

This reduces Python API churn and allows the C++ implementation to evolve independently.

## Phase 7: Scripting and Research

Phase 7 ([Roadmap](../roadmap.md#9-phase-7-python-research-layer)) is designed around two uses of one `oryx` API:

* **Scripting, Unity-style:** a game or strategy defined in a Python file runs inside the C++ `Oasis` executable exactly like a C++ one.
* **Research and prototyping:** `import oryx` from a REPL, script or notebook, with a Python prototype later portable to C++ behind the same registry id.

The milestone that closes the phase: **Nim written in Python, inside Oasis, plus one Python strategy that plays both Nim and TicTacToe.** Nim is a pile of `stones` (default 21) from which players alternate taking 1..`max_take` (default 3); the last taker wins. It replaced Rock-Paper-Scissors, which is simultaneous-move and hidden-information and so unsupported by the strictly-alternating, fully-visible engine ([Architecture §14](../architecture.md#14-current-architectural-unknowns)); RPS stays a later test of that open topic.

Status legend as in the [Decision Log](decision-log.md). The decisions below are working decisions from the Phase 7 brainstorm; the implementation steps that validate them are noted where relevant.

### API shape and registration

| Topic | Position | Status |
| ----- | -------- | ------ |
| Class roles | `oryx.Game`, `oryx.State` and `oryx.Strategy` are plain Python classes created by the native module (no `.py` file, no pybind11 trampolines): `Game` and `Strategy` carry a native `__init_subclass__` that registers subclasses, `State` supplies a default `action_to_string()` and is optional (states are duck-typed). Objects owned by the engine come back as `oryx.GameHandle`/`StateHandle`/`StrategyHandle`, the Python faces of the private wrappers `PyGame`/`PyState`/`PyStrategy` (the engine interfaces themselves are never bound). C++ classes backed by a script, `PyScriptedGame`/`PyScriptedState`/`PyScriptedStrategy`, implement the language-agnostic `IScriptedGame`/`IScriptedState`/`IScriptedStrategy` from `Scripting/` and hold the user's object, calling its methods by name under the GIL. A `Game` defines `new_initial_state()`; `num_players` and an optional `name` are unannotated class attributes read once when the game is created. A `State` defines `legal_actions()` (a list of ints), `apply`, `undo`, `current_player`, `is_terminal`, `action_to_string` and `outcome()`, which returns a **list of rewards**, one per player (the terminal flag comes from `is_terminal()`, so there is one source of truth). A `Strategy` defines `decide(context)` returning an action | Working decision |
| Registries | Gymnasium-style: `oryx.make_game("tictactoe")`, `oryx.make_strategy("random", seed=1)`. Python registrations go into the same `Registry<T>` as C++ ones, so Oasis's menu lists them | Working decision |
| Core bindings | The native module `oryx` (also the future extension) has submodules `errors`, `game`, `registry`, `results`, `simulation`, `random`, `math`, `benchmark` and `debug`; the public names of `errors`, `game`, `registry`, `results`, `simulation` and `random` are also reachable at the top level, from one list in `BindOryx.cpp`, so `oryx.Match` is `oryx.simulation.Match`; `debug`, `math` and `benchmark` stay namespaced (a top-level `benchmark` function would shadow the `oryx.benchmark` submodule). It exposes `make_game`/`make_strategy` (keyword arguments are the parameters), `list_games`/`list_strategies`, `describe_game`/`describe_strategy` (description, parameter schema with `required`, origin or `None` for C++), `Match` (`state` (read-only handle), `is_terminal`, `current_player`, `outcome`, `decide`, `apply`, `undo`, `redo`, `play`, `history`), `BatchRunner`, `simulate(game, strategies, games, seed)` returning a `BatchResult` (see Results as data) and `Random`. A game or strategy argument is a registry name, a registered Python class (`oryx.Match(Nim, [MonteCarlo, "random"])`, resolved through its registry entry so seeding by name applies), a native handle or an instance of a Python subclass; `make_*`/`describe_*` take a name or a registered class. A single strategy instead of a list fills every seat (a name or class creates one per seat, a handle or instance is shared). Signatures in the stubs spell these unions out (`hints::Named<...>` in `Support/PyTypeHints.h`, since pybind11's own `TypeVar` needs a feature macro Apple Clang does not set). Both hosts expose `oryx.__version__`; `oryx.init()` exists only in the research host. The type stubs in `OryxPython/stubs/oryx/` mirror the submodules, regenerated from the built extension with `uv run --group stubs forge python stubs` (`pybind11-stubgen`, a dev-only `stubs` uv dependency group; the output folder is `[tool.oryx] stubs-dir` in `forge.toml`) rather than kept in step by hand. A test compares the public names of every module with its stub (minus the research-host-only `init`), so a binding without a stub (or the reverse) fails the build; every binder's `.def(...)` needs named `py::arg(...)`s and a description string, since the generator reads both from pybind11's auto-generated signature | Working decision (built) |
| Construction parameters | `Registry<T>::create(name, Params)`; `Params` is a string-keyed map of `bool`/`int64`/`double`/`string`; ids are unversioned. Every registration, C++ or Python, declares a schema (keys, types, defaults) so validation, `describe()` and Oasis's menu treat both alike. The registry stores the schema and a description per entry (`EntryInfo`); a bad key or type is an error naming the key | Working decision |
| Unity-style registration | `class Nim(oryx.Game, id="nim")` registers on import through `__init_subclass__` (`overwrite=True` allowed; a subclass without an `id` is an intermediate base and is not registered). Fields annotated `bool`/`int`/`float`/`str` form the schema, a class value is the default and no value means required; anything else needs `typing.ClassVar`, and `name`/`num_players` are reserved. The first line of the docstring is the description. The bases declare typed placeholder methods (`Game.new_initial_state`, `Strategy.decide(context) -> int`, and `State.legal_actions/apply/undo/current_player/is_terminal/outcome`) that raise `NotImplementedError`, so IDEs and the stubs show what to implement; the checks ignore them (`PythonContext::is_placeholder`), so a missing `new_initial_state()`/`decide()` is still a `ScriptError` at import. `__init_subclass__` takes keyword-only `id` and `overwrite`. Creating an entry runs `cls.__new__`, sets the resolved parameters as attributes, then calls `__init__()` (no arguments), so `__init__` can read its parameters. `oryx.register_game(id, factory, params=..., description=..., overwrite=...)` and `register_strategy` register factory functions, which receive the parameters as keywords; `params` maps a name to its default, or to `bool`/`int`/`float`/`str` for a required one | Working decision (built) |
| Required parameters | `ParamSpec::required` marks a parameter that has no default and must be given; `resolve_params` is the one place that enforces it (`ParamError ... is required`), for C++ and Python entries alike. A parameter without a default that is not required (such as `random`'s `seed`) is optional. Oasis omits entries with required parameters from its menus (it cannot supply them yet, there is no `--param`) and reports a clear error when one is named on the command line | Working decision (built) |
| Origin-tagged registration | Research needs notebook-safe re-registration: re-running a cell that redefines `class Nim(oryx.Game, id="nim")` replaces the entry when the origin (language, module, source file) is the same; a clash with an entry of another origin, including a C++ one, is a `ScriptError` unless `overwrite=True`. Built in `Scripting/ScriptRegistry.h` as free functions over `Registry<IGame>`/`Registry<IStrategy>` with a side table of origins, not in the core `Registry<T>`. `unregister_scripted(language)` drops a language's entries, and `PythonRuntime::stop()` calls it before finalising the interpreter so no factory outlives the objects it holds. Overwriting a C++ (or another origin's) entry with `overwrite=True` restores it once the clobbering runtime's language is unregistered, through a per-id stash stack: unregistering a language drops all of its layers and restores the topmost remaining entry, so a chain (A overwrites C++, B overwrites A) gives back A when B's language stops and C++ when A's does, including after a reload | Working decision (built) |
| Seeding | `simulate(seed=S)`: strategies created by name that declare a `seed` parameter get `S + seat_index` (`seeded_params()` in `Scripting/`); instances passed in are user-seeded; no change to `IStrategy` or `BatchRunner`. Recording the master seed in the results is part of the results-as-data work; `BatchResult` does not carry it yet | Working decision |
| Logging and assertions | One Tier 1 submodule, `oryx.debug`, bound in one file (`BindDebug.cpp`). `oryx.debug.trace/info/warn/error/critical(message)` call the Core `Log::message` (always formatted with `"{}"`, so script text is never a format string) and route to the client logger so script output interleaves with engine output; `oryx.debug.install()` attaches a `logging.Handler` bridge. `oryx.debug.check(condition, message="")` calls Core `check`, which raises `OryxAssertionError` in every profile without logging by itself (an uncaught one is reported by the layer or runtime boundary, once). A C++ `OX_ASSERT` uses the same assertion handler; `oryx.init()` (research host) installs the throwing one, see the assertion hook below | Working decision (built) |
| Initialisation and guard | The guard machinery is language-agnostic and lives in `Scripting/Support/InitGuard.h`: `OX_GUARDED_FUNC(function, name)` yields a function pointer with the same signature whose check is one inline load with an `[[unlikely]]` branch and an out-of-line cold throw of `oryx::NotInitialisedError` (`oryx.debug.info() was called before Oryx was initialised`; `oryx.NotInitialisedError` in Python). It covers every entry point that would otherwise dereference a logger that does not exist yet: `oryx.debug.*`, `make_game`/`make_strategy`, `list_*`, `describe_*`, `Match`, `BatchRunner` and `simulate`. The message goes in the exception, not the log, because the guard fires exactly when no logger exists. Free functions only; the fixed `Args...` signature is required so pybind11 can deduce the Python signature. Scripts embedded in Oasis never call `oryx.init()`, because Oasis's `main()` already did; the embedded module has no `init()` at all | Working decision |
| Research-host lifecycle | `oryx.init(settings=None)` (research host only) calls `oryx::init()`, installs `throw_on_assertion`, then reads `settings` or else the nearest `oryx.yaml` above the working directory (none: nothing is loaded) and imports every script under its `scripting.roots`, putting each root on `sys.path` — the same settings and discovery Oasis uses (`Support/PyScripts`), so a notebook needs no path setup or script imports. Importing the extension registers an `atexit` teardown that runs before the interpreter finalises: it drops Python-defined registrations (restoring anything they overwrote), resets `PythonContext` and the per-class method cache, and marks the context shut down, so a later use (an `atexit` handler registered before `import oryx`, a finaliser) raises `OryxError` instead of re-creating Python objects during finalisation. `benchmark(memory=True)` works in both hosts: it reads the counts of Oryx's default allocator ([Memory Allocator](memory-allocator.md)) | Working decision (built) |
| Module tiers | Tier 1: game, strategy, registry, simulation (`Match`/`BatchRunner`/`BatchResult` and `simulate()`), random, results, debug (logging and checks). Tier 2: math (`Vec`/`Mat`, buffer protocol and numpy), benchmark. Not exposed: `Application`, `Layer`, `Event` | Working direction |
| Results as data | The Python `BatchResult` (`oryx.results`) keeps `matches`, `wins`, `draws`, `rewards` and `decisions` as plain values and adds `win_rates`, `draw_rate`, `mean_rewards` (the C++ `win_rate`, `draw_rate` and `mean_reward` in `BatchRunner.h`), `metadata`, `to_dict()`, `to_numpy()`, `to_dataframe()` (one row per player, the totals in `frame.attrs`), `__repr__` and `_repr_html_()` (an escaped table for notebooks). `metadata` is filled by `simulate()` and `benchmark()` (game, strategy names as given or the Python type name of an instance, games, seed or `None`, Oryx version) and is `None` for a hand-built `BatchRunner`. The C++ `BatchResult` in Core is unchanged; the metadata lives in the binding, so nothing that outlives the interpreter holds a Python object | Working decision (built) |
| Math module | `oryx.math` exposes `Vec2/3/4` and `Mat2/3/4` over `double` (the `*d` aliases), constructors from components, one value or a sequence, `x/y/z/w`, indexing, arithmetic, `dot`, `cross`, `lerp`, `approx_equal`, length and distance, `@` for matrix products, `determinant` and `inverse` (2x2 and 3x3), and the buffer protocol, plus scalar helpers and constants (`clamp`, `lerp`, `radians`, `PI`, ...). `inverse()` checks the determinant first and raises `OryxError`, because the C++ `OX_CORE_ASSERT` would trap in Debug. **Adding a math item:** a new size or scalar type is one line in `kVectors`/`kMatrices` in `BindMath.cpp` (names, operators and buffer come from the templates in `BindMath.h`; a new scalar type also needs a suffix in `scalar_suffix()`); a new kind of type is one `bind_<thing>(module)` function added to `kOneOffs`; a free function is one `module.def` line in `bind_scalar_functions`; each also needs its lines in `stubs/oryx/math.pyi`, which the stub test enforces | Working decision (built) |
| Benchmark module | `oryx.benchmark.benchmark(game, strategies, games, seed, memory)` runs a batch like `simulate()` on the C++ `BenchmarkRunner`/`MemoryBenchmarkRunner` and returns a `BenchmarkResult` (`outcome`, `elapsed_seconds`, `matches_per_second`, `decisions_per_second`, and a `MemoryStats` when `memory=True`); `Timer` is also a context manager. Memory counts C++ allocations made through Oryx's tracker, not Python's allocator. It shares the game/strategy resolution and the GIL rule with `simulate()` (`Support/PyBatch`) | Working decision (built) |

### The scripting seam

| Topic | Position | Status |
| ----- | -------- | ------ |
| `Scripting/` module | `Oryx/src/Oryx/Scripting/` is a full, language-agnostic module, always compiled and free of any Python dependency, in three folders: `Interfaces/` (`IScriptRuntime`: `running`, start/stop, load, reload, unload, file extensions, language; `IScriptedGame`/`IScriptedState`/`IScriptedStrategy`), `Registry/` (`ScriptRegistry`, `ScriptRuntimeRegistry`) and `Support/` (`ScriptSource`, `ScriptOrigin`, `ScriptError`, `ScriptLease`, `ScriptUtil`, `InitGuard`), plus `ScriptDiscovery`, `ScriptSettings` and the public `ScriptingLayer : Layer` at the root. `ScriptUtil` holds the rules every runtime shares and that are unit-tested without Python: `check_legal` (a script may only play a listed action), `outcome_from_rewards`, `involves_script`, `seeded_params`, `describe`. The Python backend builds on it | Working decision |
| Built before a second implementation | The repository's precedent (`IBoard`, the `Registry<T>` timing) is to wait for a second implementation before extracting an interface. This seam is built with one implementation (Python) **by choice**: it keeps public headers and applications free of language names and confines the Python on/off switch to the backend, so a further runtime needs no public change. It is a deliberate exception to the [Design Review Principle](principles.md#design-review-principle), not a new default | Working decision (deliberate exception) |
| Reload | `ReloadScriptsEvent` (`Events/ScriptEvent.h`) is handled by `ScriptingLayer`, which reloads the settings (a bad `oryx.yaml` is logged and the previous roots stay), re-runs discovery, calls `IScriptRuntime::unload()` on each running runtime and then `reload()` for each source, starting a runtime that had no sources before. `PythonRuntime::unload()` drops every scripted registration, removes every module under a script root from `sys.modules` (helper modules included, so they run again and their registrations return) and takes the roots off `sys.path`. A source that fails is logged and the rest still reload, but its entries are gone until it is fixed (reload is unload-then-reload, not transactional). Games and strategies already in play keep their Python objects, only new creations see the new definitions. Oasis has no trigger yet (the event is posted by whatever hosts the layer; a console or GUI command belongs with the input work) | Working decision (built) |
| Runtime lookup | `PythonRuntime` registers itself as `"python"` in `ScriptRuntimeRegistry` (`OX_REGISTER_SCRIPT_RUNTIME`), alongside `OX_REGISTER_GAME`/`OX_REGISTER_STRATEGY`. `ScriptingLayer` is deliberately simple: it discovers sources, creates one runtime per discovered language from the registry and loads the sources; a runtime is started only when it has sources. There is no `PythonScriptingLayer` and no Python macro in public headers; Oasis names no Python type. With Python off no `"python"` runtime registers | Working decision |
| Script discovery | A script is a plain `.py` file under a **script root**; location, not a file-name marker, decides what is a script. Roots come from the `scripting:` section of `oryx.yaml` (`ScriptSettings::roots`) and from `--script-root <dir>`; a `--script <file>` outside every root uses its own directory, and `--module <name>` imports by name. Nothing is scanned when no root is configured. A file or directory starting with `_` or `.` is a helper: importable, never loaded on its own (`_common.py`). The Python runtime appends the root to `sys.path` and imports the script by its real dotted name (`deeper/alpha.py` is `deeper.alpha`), then checks `module.__file__`: a script that a standard-library module or another root shadows (`random.py`, two roots defining `nim`) is a `ScriptError` telling the author to rename it, and a dot in a script's name is rejected. Scripts can therefore import each other and run standalone. Installed packages through Python entry points (`oryx.games`/`oryx.strategies`) stay **deferred until packages can be installed** (wheels/PyPI, out of Phase 7). Under plain `import oryx` no discovery is needed: the user's own `import my_game` registers it. A "no runtime for `.py`" message is logged only for explicitly named sources | Working decision (built) |

### Ownership, lifetime and errors

| Topic | Position | Status |
| ----- | -------- | ------ |
| Ownership and lifetime | Scoped to scripting. Adapters (`PyScripted*`) hold a `PyScriptObject`, which releases its object under the GIL and leaks it instead once the interpreter is finalised, and forward calls through `PyGil`, which throws a `ScriptError` when the interpreter is not running. A `State`, `Context` or `ActionFeatures` lent to a strategy is a handle guarded by a `ScriptLease` that is armed only during `decide()`; later use raises `OryxError`, and the state handle of a `Match` is read-only so it cannot bypass the match history. Factories held by Python are dropped by `unregister_scripted` before finalisation. Still open: how a pure-Python host owns C++ objects handed back to it | Working decision (scoped to scripting) |
| Script errors | A script exception raised inside a Python-backed game, state or strategy becomes a `ScriptError` carrying the traceback, propagates to a layer boundary and is logged there ([Error Handling](cpp-api.md#error-handling)); the layer is disabled, `Application::on_layer_disabled` runs, and `OasisApp` closes with exit code 1, so Oasis ends promptly instead of spinning. A Python caller of `simulate()` or `Match` sees `oryx.ScriptError` (with `.detail`), not the original exception type, **except** `KeyboardInterrupt`, `SystemExit`, `GeneratorExit`, `MemoryError` and `RecursionError`, which reach the Python caller untouched (the embedded load path still wraps them, so a script's `sys.exit()` cannot disable the scripting layer). The binding never lets a script reach an assertion or undefined behaviour: `apply()` on a native or lent state and `Match.apply()` check the action against `legal_actions()`, a Python strategy that returns an illegal action (the `INVALID_ACTION` sentinel included) is an `IllegalActionError` (a `ScriptError`), and a wrong-typed result names the method and the type (`state.current_player(): expected an int, got str`) | Working decision (built) |
| Exception types | `oryx.errors`, re-exported at the top level: `OryxError(Exception)`; `ParamError(OryxError, ValueError)` with `.key`; `ScriptError(OryxError)` with the traceback in `.detail`; `IllegalActionError(ScriptError, ValueError)`; `OryxAssertionError(OryxError, AssertionError)`; `SettingsError(OryxError)`; `NotInitialisedError(OryxError, RuntimeError)`. Each maps from a C++ `oryx::Error` subclass by its `category()` in `translate_error` (`BindErrors.cpp`); the builtin bases let generic handlers such as `except ValueError` work | Working decision (built) |
| Speed | A Python-defined `State` inside C++ Minimax crosses the boundary on every `apply`/`undo`/`legal_actions`: correct but slow. Each scripted class gets a method table built once (compile-time method sets, `PyObject_Vectorcall`), so an adapter call is tens of nanoseconds; the last `legal_actions()` result of a scripted state is cached until its `apply`/`undo`, which also makes the legality check of `apply()` nearly free (contract: a scripted state changes only through the engine's `apply`/`undo`). C++ games with Python strategies, and all-C++ batches, are the fast paths. `simulate`, `BatchRunner.run` and `Match.play` release the GIL when no participant is script-backed (`involves_script()`); the engine is single-threaded, so adapters rely on the reentrant GIL. Measured numbers are in [Quality](quality.md) | Documented limit |
| Interruptible batches | `simulate()`, `BatchRunner.run()` and `benchmark()` share one chunked loop (`run_interruptible()`, `Support/PyBatch`) instead of one monolithic `BatchRunner::run(match_count)` call: chunks start at 1 match, the GIL releases around each chunk unless a participant is script-backed, and `PyErr_CheckSignals()` runs between chunks — a pending interrupt raises `KeyboardInterrupt` and discards the partial batch. Chunk size re-estimates from the previous chunk's wall time (target ~50 ms, growth capped at 2x), so Ctrl-C latency stays roughly constant whether the game is trivial or a slow search strategy, which a fixed chunk count cannot do. Needs a Core `merge(BatchResult&, const BatchResult&)` next to `accumulate()` (sizes an empty result from the other, so a chunked run merged piece by piece equals one `run(match_count)` call) and starts from `runner.run(0)` so `games=0` keeps its correctly-sized empty result. Inert in embedded Oasis: `PythonRuntime::start()` sets `install_signal_handlers = 0`, so `PyErr_CheckSignals()` there never observes a pending signal unless the script installs its own handler | Working decision (built) |
| Shutdown and runtime ownership | `oryx::shutdown()` (`Application.h`) runs generic shutdown hooks once, in reverse registration order, after the `Application` and so every layer and adapter is destroyed; `EntryPoint.h` calls it. Runtimes are process-wide, owned by `ScriptRuntimeRegistry`; `ScriptingLayer` only drives them (its explicit-runtimes constructor takes non-owning pointers, for tests). The first `ScriptRuntimeRegistry::start()` of a runtime registers a hook that stops it, so `Py_Finalize` runs with nothing left to leak. `PythonRuntime::stop()` warns when script objects are still alive at that point. Research host: `import oryx` runs inside an existing interpreter, so no runtime starts or stops there | Working decision (built) |
| Adding a scripted interface | Checklist: (1) the language-neutral interface in `Scripting/Interfaces/`; (2) one `PyMethods<Owner, Required, "name"...>` set in `Interop/PyMethods.h` (a typo is a compile error, required methods are checked when the class is first used); (3) one adapter deriving from `PyAdapter<Set>` in `PyScripted`, calling `call<"name", Result>(args...)` with types `PyConvert` knows; (4) one `Bind*.cpp` registered in the `kBinders` table of `BindOryx.cpp`, its names re-exported there and listed in the stub; (5) rules other runtimes must share go into `Scripting/ScriptUtil` with a Python-free test | Working decision |

### Research and prototyping

Research use is a first-class requirement, not a by-product:

* **Frictionless import:** after a successful compile, `build_system` writes a generated `.pth` file (`oryx_research_host.pth`) into the active venv's site-packages, pointing at `OryxPython`'s output directory, so `uv run python`, Jupyter and the REPL find `import oryx` with no path work and no manual install step. Wheels and PyPI are a later packaging phase.
* **Interactive stepping:** the Python `Match` exposes `decide()`/`apply()`/`undo()`/`redo()`/`history`, as the C++ `Match` does.
* **One-liner simulation:** `oryx.simulate(game, strategies, games=10_000, seed=...)` returns a `BatchResult`; this covers Phase 7's "configure experiments / access statistics" minimally, and full `Experiment` and sweeps stay Phase 8.
* **Results as data:** built, see the table above (`to_dict()`, `to_numpy()`, `to_dataframe()`, `_repr_html_()`, rates and run metadata).
* **Long runs stay usable:** all-C++ batches release the GIL; chunked execution (see Interruptible batches above) means Ctrl-C or a notebook interrupt raises `KeyboardInterrupt` mid-batch instead of blocking until it finishes.
* **Introspection:** `list_games()`, `list_strategies()`, `describe("nim")` (schema and origin), docstrings and `.pyi` stubs.
* **Graduation path:** a Python prototype and its C++ port share the ABC contract, the registry id and the schema, so call sites do not change; differential testing (same seeds, both implementations, compare `BatchResult`) validates a port.
