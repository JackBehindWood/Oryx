# Dashboard (Phase 11)

> **Status: Step 1 (scissor), Step 2 (`Interface/Canvas/` drawing, core, layout and shared widgets, `Interface/UI/`, and the Oasis board overlay ported to it) and Step 3 (`Interface/GUI/`: Sessions 1-4, Canvas foundation, interaction and `state<T>`, widgets and popup layer, data widgets) are built, pending the user's check of the real window (Oasis keeps the GUI showcase under its Help menu). Step 4 (`Dashboard/Feed`: `DashboardFeed`, records, `DashboardModel`) is built, headless. Step 5 (`Dashboard/View`: `IDashboardView`, registration, probabilities and values views) is built. Step 6 (Oasis wiring: input routing, view regions, observer path, GUI workspace and modal, `Dashboard/Panel`, `OasisShell`) is built and green; only the user's check of the Metal window is open. Step 6b Session 1 (`Interface/GUI/Dock/`: the headless dock core) is built.** The step-by-step tracker lives with the implementation plan; this page records the design and the reasons behind it.

Phase 11 adds a live in-window Strategy Dashboard. This page covers the module layout, the UI and GUI systems it needs, the scissor/clipping work in the renderer, and the industry survey the choices come from. See also [Observability](observability.md) for the data it consumes and [Graphics](graphics.md) for the renderer it draws through.

Phase 9 gave observability (`IDecisionObserver`, `Decision`, sinks); Phase 10 gave graphics (`SceneRenderer`, `RenderSource`, `DebugRenderer`, bitmap text, Oasis windowed boards). Phase 11 makes algorithm behaviour visible in a live in-window dashboard. It consumes only `Decision` data, is headless-testable through `NullRHI`, and costs nothing when detached.

Four modules, in dependency order (the first three are folders of one group, `Interface/Canvas/`, `Interface/UI/` and later `Interface/GUI/`; the paragraphs below use the short names), each usable without the ones above it. `UI` and `GUI` are **two peer systems**, both immediate-mode in the Dear ImGui spirit, with different audiences (the Unity split of player UI vs IMGUI/editor tooling):
1. **`Interface/Canvas/`**: the shared layer under both systems. Drawing: `Rect`, a recorded `DrawList` (typed command arrays, channels, a clip per command), `Painter` (rect, rounded rect, border, line, text with clip/ellipsis) and `replay` into `BatchRenderer2D`. Core: `ImContext` base (input, ids, hot/active/focus, frame arena), `ImTheme` base data, `StateTable`. Layout (`LayoutTree`, Clay-style sizing and floating boxes, solved and painted at `end_frame`) and the shared `im::` widgets (label, button, toggle, panel, status line) live here too, so UI and GUI share one implementation; widgets take their look from the `ImTheme` they are given.
2. **`UI/`**: *player-facing* immediate-mode system: themed, anchored, game-like (board buttons, status, menus, HUD). Few widgets, generous spacing, anchor-based layout, designed to be styled per game.
3. **`GUI/`**: *developer-tooling* immediate-mode system: dense, dockable, tool-like (dashboard, inspectors). Rich widget set, panel/dock host, tooltips, tables.
4. **`Dashboard/`**: a consumer and extension point (feed, built-in views, a view API users extend). It uses `GUI/` and is unknown to `Interface/Canvas/`, `UI/` and `GUI/`.

### Where ImGui is too restrictive, and what we do about it
1. Global context pointer is unguarded -> private active context, scoped swap (`GuiContextScope`), debug check that a frame is open.
2. Style is global and enum-indexed -> `Theme` struct plus per-widget `Style` overrides.
3. Custom widgets need internals -> a public item/behaviour API our own widgets use.
4. Layout cannot know sizes before emitting -> `UI/` layout has measure/arrange; retained size cache gives scroll extents without a one-frame lag where content size is known.
5. Id collisions via label strings -> typed ids (`ImId` in the shared layer, distinct `UiId`/`GuiId` built from `TypedId<Tag>`, a pinned FNV-1a hash, a per-context salt), explicit scopes, an always-on duplicate-id check (one comparison against the item's last-seen frame, no per-frame list).
6. Layout persistence is string-keyed ini -> versioned typed layout record.
7. Platform/draw coupling -> draws only through `Painter`/`BatchRenderer2D`, tested on `NullRHI`.

## Architecture
Layering: `Graphics -> Shaders -> Renderer -> Canvas -> {UI, GUI}` (all under `Interface/`); `GUI -> Dashboard`; `Board/Graphics -> UI`. `UI` and `GUI` never include each other. Add `[boundaries]` rules in `forge.toml` for each edge (`forge boundaries check`).

- **`Interface/Canvas/` (shared base, built in Step 2 sessions 1-2):** `Rect`/`Insets`/`CornerRadius` (logical points, origin top-left, y down; free functions). `DrawList` records commands in typed per-primitive arrays plus an ordered run list (no tagged union, so GUI adds `polyline` as one struct, one array and one replay function), with z-order channels, a surface id and the clip in effect per command; commands outside the clip or without area are not recorded. `Painter` records through it (pixel-snapped rects, text boxed with clip or ellipsis). `replay(list, batcher, font, ReplayTarget{origin, window})` flips y once, emits through `BatchRenderer2D`'s single GUI stream (`draw_ui_*`: one pipeline for rects, lines, text, images and signed-distance rounded fills/borders; scissor via `push_clip`) and changes the scissor only when the clip index changes; `dump(list)` gives deterministic text for golden tests. `ImContext` (concrete, non-polymorphic, protected destructor; `UiContext` and `GuiContext` derive) holds the `ImInput` of the frame, the id stack, hot/active/focus with `wants_mouse`/`wants_keyboard`, a `FrameArena`, the `DrawList`, a copy of the `ImTheme` base, and a `StateTable<ItemMemory>` that gives each item's previous-frame rect. `item(id, rect)` hit-tests the rect (grown to `min_hit_size`) inside the current clip, so a scrolled-out widget is never hovered. `ActiveContext<T>`/`ContextScope<T>` give each derived type its own private active slot. One context per surface (the multi-viewport seam).
- **`Interface/Canvas` layout (built, Step 2 session 3):** `LayoutTree` in the manner of Clay. A box is `Sizing` per axis (`fixed`, `fit`, `grow` with a weight, `percent`, each with min/max), a direction, padding, gap, per-axis child alignment, an optional aspect ratio, `overflow` clip and a z channel; a `Floating` box leaves the flow and attaches one of nine points of itself to one of nine points of the parent, the surface or an earlier element. `end_frame` solves bottom-up (fit sizes, text through a measure callback that is zero while the font is not ready), then top-down (percent, grow by weight, compress the largest first down to the minimum, alignment, floating) and paints the boxes into the `DrawList`; boxes with an id leave their rect for the next frame, which `item(id)` hit-tests (one frame late, no hit on a box's first frame). No margin, wrap, grid or scroll. `dump_layout` gives golden text.
- **`Interface/UI/` (player-facing, immediate-mode, built in Step 2 session 4):** `UiContext : ImContext` (private active slot, `ContextScope<UiContext>`), `UiTheme : ImTheme` (adds `spacing` and a `status` style), thin `oryx::ui` functions over the shared `im::` widgets, `ui::item(id, rect)` for custom widgets and `ui::anchored(...)` for floating boxes. The widgets report `ItemState` from the previous frame's rects, so a click is returned in the frame it happens.
- **Oasis dogfooding (built, Step 2 session 5):** `Board/Graphics/BoardOverlay2D` builds the board overlay as three free-form layers over the surface, with no row or column container: a full-surface `overlay` box padded by the status band, menu band and gutters whose inner `board` box is the area `fit_board_2d(scene, viewport, region)` fits the board into; the status line floated at `TopCentre` (`StatusOptions::margin` centres it in the band); and an `options` strip floated at `BottomCentre` whose 120x36 buttons flow with a 12 point gap. `run_board_overlay` runs the whole frame (`begin_frame`, build, `end_frame`) in `PresentedGraphicsBoard2D::update`, then reads the board area from that frame's solve, so the board is never a frame behind a resize and only the buttons answer from the previous frame's rects. `BoardInput` gained `scale`; `board_input_to_im` maps it to `ImInput` and hides the pointer from the widgets while a board drag owns it. `render_stage(Overlay)` only `replay`s the context's `DrawList`. `BoardTheme2D` carries a `UiTheme` (`board_ui_theme()`, the flat look of the old overlay). Buttons now fire on release like every toolkit's. Removed: `draw_board_overlay_2d`, `OptionButton2D`, `option_button(s)_2d`, `option_at`.
- **`GUI/` widgets (built, Step 3 sessions 3 and 4):** basics (`text_coloured`, `bullet`, `key_value`, `small_button`, `checkbox`, `radio`, `selectable`, `badge`, `colour_swatch`, `progress`), structure (`collapsing_header`, `begin_tree_node`, `begin_scroll`, `TabBarScope`, `splitter`, `ListBoxScope`, `filter_matches`), input (`slider_*`, `drag_*`, `ComboScope`) and menus/overlays (`begin_menu_bar`, `begin_menu`, `menu_item`, `begin_popup`, `context_menu`, `tooltip`, `toast`, `inspector`). Labels come first by default (`GuiTheme::label_side`); popups draw on the reserved popup/tooltip channels and leave their ancestors' clips. See the decision-log rows "GUI widget set and shapes" and "popup layer and overlay channels".
- **`GUI/` (developer tooling, immediate-mode):** `GuiContext` (same active-context pattern), hashed id stack + hot/active/focus, `wants_mouse`/`wants_keyboard`, per-id state table with generation GC, frame arena, measure/arrange layout with cursor escape hatch, public item API (`item_add` -> `ItemState{hovered, pressed, held, clicked}`) used by our own widgets, widgets (label, button, toggle, collapsing header, scroll region, bar, line plot, table, tooltip), `PanelHost` (dock regions, tabs, drag, versioned layout save). `GuiTheme` (dense dark default, independent of `UiTheme`).
- **`Dashboard/`:** `DashboardFeed : IDecisionObserver` (bounded ring of `DashboardRecord`, labels captured at `on_decision` via `IState::action_to_string`, aggregates through `DiagnosticsAggregator`); `DashboardModel` (read-only view of feed + selection); `IDashboardView` + factory registration; built-in views; `Dashboard/Panel`, stateless functions (`make_panel_state`, `draw_dashboard`) that draw the registered views under collapsible headers on the active `GuiContext`. `Oasis/Core/OasisShell` is the `IFrameClient` and `RenderSource`: it owns the shell `GuiContext`, menu bar, feed, model and Showcase hosting. Not an extra layer, not in `BoardLayer`.
- **`Dashboard/Feed` (built, Step 4; headless, builds with `--without graphics`):** `DashboardFeed : IDecisionObserver` is a bounded ring of plain-data `DashboardRecord`s over fixed pools sized once by `FeedOptions` (`capacity` 256, `max_scores` 64, `max_metrics` 32, `max_keys` 128, `max_tree_nodes` 0): the constructor/`reset` allocate, `on_decision` does not (the one exception is the first sighting of a diagnostic key, which interns its name). A record holds `sequence` (monotonic, never reused, even across `clear`), `match_index`/`decision_index` (the feed cannot know the game ply, so decisions are numbered within the match; `begin_match` starts a new one), player, chosen action and label, `chosen_value`/`chosen_probability` as `float` (NaN when absent, so GUI `Values` can stride over the record array with `data()` and `first_slot()`), and counts into the score (`ScoreEntry` with a 24-byte `FixedLabel` taken from `IState::action_to_string` at `on_decision`), metric (`MetricEntry{key id, value}`) and capped `SearchNode` pools. Diagnostic keys are interned to `uint16_t` ids with per-key `KeyStats` (sum, max, last, count; `_max` keys keep the maximum); `key_namespace` groups by the text before the first `/`. Overflow of scores, metrics, keys or tree nodes is counted (`dropped_*`, `drops()`) and never thrown, and keys are not validated (`nokey` or `wins/0` are kept), so a display sink cannot abort a `Match`. `RecordView` is pointers plus counts. `DashboardModel{ feed, selected_sequence, follow_latest }` with `select_record`, `follow_latest_record` and `selected_view` is separate from the feed so one selection can serve several surfaces. Attach and detach are `Match::set_observer(&feed)` / `nullptr`; there is no new core hook. The producer still allocates when attached (`Decision::extra` is a `std::map`); measuring that is Step 9.
- **`Dashboard/View` (built, Step 5; graphics set):** `IDashboardView` has two pure virtuals, `title()` and `draw(DashboardModel&)`; the view draws its body on the active `GuiContext` and the host owns the header, size and placement. Views register through `Registry<IDashboardView>` (`OX_REGISTER_DASHBOARD_VIEW(Type, "id")`, ids `probabilities` and `values`; custom ones use `namespace/name`); the built-ins are private to their `.cpp` and reached by id. A view reads only `RecordView` (labels, probabilities, values, NaN for absent), so it names no game, action count or board; missing data is an empty-state label. `probabilities` draws one percent bar per scored action with the chosen one at full accent inside a scroll region; `values` draws diverging bars scaled per record by the largest magnitude (raw number printed) and a plot of `chosen_value` over the ring, where a click selects that record through `select_record`. `Dashboard/View` may not include `Board` or `Assets`.
- **Never inline strategy/game knowledge:** the feed copies; the dashboard sees only `Decision` + labels.

## Oasis wiring and end-to-end integration (built, Step 6)
Tic-Tac-Toe vs Minimax (or any registered game and opponent) shows the board plus a live dashboard in graphical Oasis. Headless, `--simulate`, console (`--no-window`, `--without graphics`) and Python launches never create the shell, the feed or the router's views.
- **Frame phases.** `GraphicsLayer` runs `FramePhase::Interface` clients (the shell, the Showcase) first, then `World` clients (boards) with a `FrameInfo` of their view. `SceneRenderer` orders sources by draw layer, so interface sources draw above boards although they ran first.
- **Input routing.** `InputRouter` (Core, headless) holds per-frame pointer/keyboard claims and a press latch: a press belongs to whoever it began on until every button is up. Dragging from the panel over the board, or from the board over the panel, never clicks a cell. A claimed keyboard (text focus, open menu, modal) hides keys, Esc included, from the world.
- **View regions.** The shell's `GuiWorkspace` (menu bar, optional right side panel, central area) reports the central rect; the shell passes it to `InputRouter::set_view(k_main_view, ...)`. The board is a true sub-viewport: region-sized surface, region-local cursor, region camera and clip. Board code knows nothing about the panel.
- **Modal arbitration.** `gui::open_modal`/`begin_modal`/`confirm` draw a dimmed backdrop and claim pointer and keyboard; Esc cancels.
- **Match switching.** Game and Opponent menus list `selection::creatable_games()` / `opponents_for(game)`, so a newly registered game appears with no Oasis edit. A switch is a `StartMatchEvent` recorded by `BoardLayer::event` and applied at the top of `BoardLayer::update`. Once a move was played the shell asks first (Switch / Cancel); there is no Save (serialisation is an open question, architecture §14). The feed is cleared when the new match begins.
- **Dashboard and Showcase.** `--dashboard` / `--no-dashboard` override `dashboard.enabled`; the View menu toggles at runtime. `Help > GUI Showcase` replaces the right panel and opens at half the surface (the widest a side panel goes) until it gets its own viewport. The panel header shows the match number and decisions seen; each view sits under its own collapsible header.
- **Known limits.** Item hit areas lag one frame; the feed is attached for the whole graphical run; `history` is read at construction; the panel width is fixed until `PanelHost` (6b).

## Step 6b: dock system (`Interface/GUI/Dock/`, Session 1 built: the headless core)
Plan and session tracker: `.claude/plans/step-6b-panelhost-plan.md`. Session 1 is pure data and functions with no context or drawing; later sessions add YAML, the `PanelHost` rendering, drag and the Oasis wiring.
- **Data.** `DockLayout` is flat, fixed-capacity and trivially copyable (64 nodes, 8 tabs per stack, 8 floats, 32 homes, 2 surface roots): nodes are `Empty`, `Split{axis, mode Ratio|FixedFirst|FixedSecond, ratio, points, first, second}` or `Tabs{ids, selected, collapsed}`. Binary splits only; a same-axis chain looks n-ary. `normalize` rewrites nodes in depth-first order, so equal layouts compare equal and `dump`/`diff` give golden text. `PanelId` is a 32-bit FNV-1a hash; names and titles live in the registered `PanelDesc`, not in the layout.
- **Permissions.** `PanelFlags` are six independent bits (`reorder_in_host`, `dock_elsewhere`, `tear_off`, `resize`, `collapse`, `close`) checked by one `can_*` set shared by the operations, cursor/preview feedback and tests. A pinned panel clears `dock_elsewhere` and `tear_off` yet still reorders and resizes. A splitter is adjustable when each side holds at least one resize-capable panel; a Tabs node collapses only when every tab allows it.
- **Operations.** `dock_panel`, `float_panel`, `close_panel` (records a `DockHome`), `open_panel`, `reorder_tab`, `select_tab`, `set_collapsed`, `set_split` each take the layout and the panel table and return `DockResult{applied, reason}`. A refusal never throws and leaves the layout untouched; `validate` throws `oryx::Error` only for corrupt data. `LayoutHistory` is a fixed ring of snapshots for undo/redo.
- **Geometry.** `solve` gives a rect per node, tab strip and body, uniform tab rects (scrolling to keep the selected tab visible when they do not fit) and floats clamped inside the surface; per-panel minimums propagate bottom-up once and a surface smaller than the minimums shrinks both sides proportionally. `drop_target` returns the node, zone and a preview rect equal to the rect the dock would take.

## Step 3 built (`Interface/GUI/`)
The developer-tooling system is complete for what Steps 4-9 consume. Sessions: 1 Canvas foundation (typed ids, wheel and keys, scroll, row/column sugar, `item_at`), 2 interaction and the widget kit (`item_drag`, `state<T>`, `canvas`, `GuiContext`, `gui::` wrappers), 3 widgets and the popup layer, 4 data widgets and the review below. The decision log has one row per decision.

**Data API (Session 4), in the manner of ImGui/ImPlot and with no callbacks, `std::function` or `std::span` in anything new.** Numbers come in as `Values { data, count, offset, stride }`, a view of the caller's floats: an array, a ring buffer (`offset` is the oldest sample) or one field of a record array (`stride` in bytes) with one type and no copy. Out-of-range reads are NaN, which every widget draws as a gap. How a number looks is plain data (`NumberFormat`, `ColourScale`, the theme's `palette`); anything stronger is the caller's own code, because an immediate-mode API already is "a callback you write inline".
- `PlotScope` opens a plot, `line()`/`bars()` add series (`Line`, `Step`, `Area`, `Points`), `vline()`/`hline()` add markers, and `area()`/`painter()` give the plot's coordinates and a clipped painter for anything else; it ends by drawing the legend and storing the y range. The range and x extent are the previous frame's, like every hit area. A pixel column draws at most its min and max sample, so a series of any length costs at most two points per column (a lone peak survives decimation). `plot_lines`, `plot_histogram` and `sparkline` are one-call forms.
- `heat_grid`/`heat_cell` colour a `Values` view by a `ColourScale` (a three-stop ramp; viridis-end-point sequential and blue-white-orange diverging defaults, both colour-blind safe) and report the hovered and clicked index.
- `TableScope` follows ImGui's table plus `ListClipper`: `column()` per column, `headers()`, then the caller loops `first_row()..last_row()` and calls `row()` and `cell()` (or `begin_cell()`/`end_cell()` around any widget). Rows have a fixed height, the scroll range spans all of them, and only the visible rows (plus one of margin) are submitted. Sortable headers only report the column and direction; the caller sorts its own data.
- `image`/`image_button` take an `ImageHandle` (an index into the owner's table of textures, `ReplayTarget::images`, or `k_single_image` with the one-texture `replay` overload); a radius (`im::circle_radius()`) shapes the picture through a textured fan on `BatchRenderer2D::draw_sprite_polygon`. They live in Canvas and are wrapped by `ui::` and `gui::`; neither names `Assets`.

**Oasis showcase.** `Oasis/src/Oasis/Core/GuiShowcase` is an `IFrameClient`/`RenderSource` owned by `OasisLayer` that draws a tabbed GUI panel (Perf with the renderer's batch and pipeline numbers, Widgets, Data) over every graphical Oasis window. It exists so the widgets can be judged in a real window. Step 6 keeps it: the Help menu of `OasisShell` toggles it and it replaces the dashboard in the right side panel; `InputRouter` keeps a click on it from reaching a board cell.

## Writing a widget
The same public calls the built-ins use are enough; `tests/unit/Interface/GUI/test_custom_widgets.cpp` runs every example below.
1. **A gizmo.** Ask for an item with an explicit rect, read the drag, paint through a `Painter` (from `gui::canvas` or a `PlotScope`):
   `const GuiId id = gui::id(name); gui::item(id, box); const ItemDrag drag = gui::item_drag(id); position = position + drag.delta;`.
2. **A stateful widget.** `gui::begin_widget(name, style)` gives the box and its `ItemState`; `gui::state<T>(gui::id("x"))` keeps a trivially copyable `T` (at most 64 bytes) under that id until a frame does not ask for it. Close with `gui::end_widget()`.
3. **A plot decoration.** Between the calls of a `PlotScope`, use `plot.area()` and `to_screen(area, x, y)` to place a band, threshold or marker with `plot.painter()`; there is no decorator type.
4. **A menu item.** A widget frame whose click calls `gui::context().request_menu_close()`.
5. **An editable widget.** Keep a `TextEditState` (caret, anchor, scroll; plain data) with `gui::state<T>`, run `text_edit_apply(buffer, capacity, state, input)` over the frame's `gui::io`-level input (`ImInput::text`, `paste`, `keys`) while your item has focus (`ctx.set_focus(id)` on a press, clear it on a press elsewhere), and draw the buffer. `gui::text_input` and `gui::input_float/int` are about a hundred lines of that. A press focuses, Enter and Escape release; ask for a clipboard copy with `ImContext::request_copy`. The editor is a pure function, so every key sequence is a unit test on data.
6. **A view.** A dashboard view is an ordinary function over its data: the `SearchView` test draws a policy as `gui::bar`s, a value history as a `PlotScope` with the selected ply as `vline`, and a trace as a `TableScope` in about twenty lines, with no allocation once warm.
Disabling: `gui::DisabledScope off(condition)` dims everything built in its scope and makes items report no hover or press, like ImGui's `BeginDisabled`.

Rules the built-ins follow and yours should: label strings are the identity under the current id scope (give repeated labels a scope with `gui::push_id`, which is also why a duplicate raises `Error`), options in, a plain result struct out, nothing allocates after the first frames (format text with `gui::context().arena().format`), and errors are thrown, not returned.

## Future-proofing, extensibility, ergonomics
- **Seams, not features:** multi-viewport (host holds no surface assumption), keyboard navigation (focus id exists), replay/external viewer (`DashboardRecord` is self-contained plain data), 3D/world-space panels (`Painter` takes a camera via the batcher, no screen assumption), Python views later (view API is plain C++ virtual; decision left open per §14), a second backend (everything goes through `DrawItem`).
- **Extensibility:** public low-level GUI API, registered views, `Theme` override, strategies add series with no dashboard code.
- **User-friendliness:** a view is about 20 lines: `if (collapsing_header(gui, "Search")) { bar(gui, "nodes", value, max); }`; sensible defaults (layout, theme, default panels); `--dashboard` just works; settings reactive like `graphics:`.
- **Performance and memory (measured by `tests/benchmark/bench_gui.cpp`, see the Step 3 notes in the decision log; the allocation checks are unit tests):** zero heap allocation per frame once warm (extend the `test_scene_renderer` allocation pattern); feed ring fixed capacity (default 256 records, `SmallVector` scores, one `Diagnostics` map each); trace list virtualised (only visible rows emitted); widgets fully outside the clip are skipped; id-state table flat and generation-collected; one vertex format, one pipeline, flush only on clip/texture change; record cost per decision when attached bounded and detached cost is the existing null check.

## Scissor / clipping API (Step 1, built)
- `RHIScissorRect {int32_t x, y; uint32_t width, height}` (framebuffer pixels, top-left) already existed in `Graphics/RHI`; `DrawItem` gained `scissor` + `has_scissor` (no `std::optional`).
- `RHICommandList::set_scissor` / `clear_scissor` (a full-extent `set_scissor`, so no new `IRHICommandContext` virtual). Validation: inside the pass attachments, non-negative, **non-empty** (callers cull empty clips). Every pass starts with the full extent: Metal's encoder default, NullRHI resets `last_scissor` at `begin_pass`, `FrameRecorder` re-derives state per pass. Metal clamps to the target as a safety net.
- There is no `BatchKey`: `BatchRenderer` flushes in `select`, and scissor changes flush through `set_scissor`/`clear_scissor` with `FlushReason::ScissorChange`. `FrameRecorder` emits set/clear only when state differs from the previous item.
- `BatchRenderer2D::push_clip(position, size)` (world-space centre and size, as `draw_rect`) resolves through the camera and `BatchTarget::framebuffer` (physical pixels, so DPI scale is covered) into pixels rounded outward, intersected with the parent clip and the framebuffer. An empty result culls draws until the matching `pop_clip`. `ClipScope` is the RAII form; `clip_scissor()` and `is_clipped(position, size)` let widgets and virtualised lists skip hidden content. `SceneRenderer` passes the routed pass's attachment size as the framebuffer.
- Industry basis (see the decision-log row "Renderer: clipping basis"): Slate/Unity/ImGui/Godot all keep clip as per-draw rect state with an intersecting stack and use scissor for axis-aligned clips; stencil and shader-side clipping (rotated, rounded, soft) are the fallbacks we do not build.
- Tests: flush on clip change, same clip no flush, nested intersection, scale-2 framebuffer, clamp/rounding, culling, `ClipScope` unwinding, recorded `SetScissor` count via NullRHI, validation errors, NullRHI per-pass reset.
