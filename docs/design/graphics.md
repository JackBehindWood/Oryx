# Graphics and Assets

> **Status: Phase 10 in progress. Steps 0-6 are built (scaffold, assets, window and input, RHI and NullRHI, Metal, shaders and pipelines, batching and the draw facade); Steps 7-10 are design only.**

Presentation is a strictly downstream concern: it reads `IState` and never the reverse. Graphics are on by default and removed with `uv run forge --without graphics <command>`. The rules below are checked by `build_system/oryx/boundaries.py` (include layering plus a symbol scan of a graphics-off `libOryx.a`), which CI runs.

## Module layout and layering

Public API in `Oryx/src/Oryx/`, namespace `oryx`:

```
Core/        **Window.h, Input.h** (abstractions + NativeWindowHandle; no GPU types); Application owns the Window
Graphics/    **new, lowest graphics layer**: RHI/ (IRHI, RHIBackend enum + create_rhi(), RHIBuffer, RHITexture,
             RHISampler, RHIShader, RHIVertexShader, RHIPixelShader, RHIPipeline, RHIRenderTarget, RHIViewport,
             RHICommandList, RHIShaderReflection) and Resources/ (GPU resource wrappers, each owns its RHI
             object: Texture2D, VertexBuffer, IndexBuffer, UniformBuffer, VertexShader, PixelShader, Pipeline,
             RenderTarget; the shader wrappers are thin: RHI shader + RHIShaderReflection)
Shaders/     **middle layer (graphics option)**: ShaderStage, ShaderSource, ShaderBinary, ShaderReflection (Shaders'
             own), Shader/VertexShader/PixelShader (one stage each), ShaderLibrary, ShaderCache, ShaderSet, IShaderCompiler + compilers (MSL, Slang later), built-in sources
Renderer/    **top layer**: Renderer (facade), BatchRenderer + BatchRenderer2D, TextureSlotTable, Camera/Camera2D, DebugRenderer and GlyphAtlas (Step 7), GraphicsLayer
Events/      **WindowEvent.h, KeyEvent.h, MouseEvent.h** (added one event per real need)
Assets/      AssetHandle<T>, AssetManager, loaders, CPU assets (ImageAsset, FontAsset, ShaderAsset)
             **GpuAssetCache.h/.cpp** (graphics option only; the one Assets file that includes Graphics)
```
Private backends in `Oryx/backends/` (**split by concern, then platform**):
```
Metal/   Metal RHI implementation (Obj-C++); takes a NativeWindowHandle, does not depend on MacOS/
MacOS/   all macOS-specific code: now Window/Input (GLFW + Cocoa glue exposing the NSWindow/NSView handle), later other platform services
Null/    NullRHI + NullWindow (records, no GPU, no display) - always built with graphics
IOS/, Windows/, Linux/, OpenGL/, Vulkan/   not created until each is actually built
```
GLFW lives in `Oryx/vendor/glfw`, used by the desktop platform backends. Vendors: `glfw`, `stb`. Oasis: `Oasis/src/Oasis/Graphics/` holds the Tic-Tac-Toe view layer.

**Dependency rules (reviewed, plus grep/link checks in CI):**
- `Core/Window.h`, `Core/Input.h`, window/input events and `Assets` (CPU) are always compiled and depend on nothing graphical; they work headless (a `Window` request with no backend resolves to NullWindow or throws a clear `Error`).
- **Strictly linear layering, enforced by include checks:** `Graphics/` -> `Shaders/` -> `Renderer/`. Each layer may include only itself, the layers below it, `Core`, `Math` and CPU `Assets`; none may include a layer above. This replaces the earlier "Renderer sandwiched around Shaders" arrangement. RHI types appear in `Renderer/` only via `Renderer::rhi()` and the resource wrappers' `rhi()` accessors.
- `Assets/GpuAssetCache` is the single edge from Assets to Graphics and produces only `Texture2D` (`GlyphAtlas`, being Renderer, builds itself from a `FontAsset`); CPU asset headers never include it. `ShaderAsset` is raw shader text + stage only (no dependency on Shaders/); `Shaders/ShaderProgram` can be built from one, so the edge is Shaders -> Assets, never the reverse.
- `Graphics/`, `Shaders/` and `Renderer/` are graphics-option only. Compilers shell out to `xcrun metal`/`slangc` and throw a clear `Error` when absent.
- `backends/Metal` and `backends/MacOS` do not include each other; they meet only through `NativeWindowHandle` (Core).
- `Game/`, `Strategy/`, `Simulation/` never include Graphics, Shaders, Renderer or Window. Public headers never include `backends/`.

## Core abstractions

```
File -> AssetManager/Loader -> CPU Asset (headless-safe)
                                  | GpuAssetCache (graphics only)
                               IRHI -> RHI resources
Window(Core) --events--> Application/LayerStack ; Input polled from Window
  game layers: Renderer facade / DebugRenderer -> batched by BatchRenderer2D into DrawItems (no RHI commands until GraphicsLayer records the frame)
GraphicsLayer (single overlay, pushed last): flush -> RHICommandList -> acquire back buffer -> submit -> present
                                             -> pump window events      [glue: sees Window + IRHI]
```

- **IRHI** (pure virtual, one instance per backend, owned, never global): the device, chosen by `create_rhi(RHIBackend)`, a plain enum (`Null`, `Metal`; `OpenGL` etc. added when built) and a `switch` guarded by per-backend defines. There is no registry. This is a deliberate, recorded deviation from the self-registering principle (decision log) until a third backend or an external backend justifies one. Factory methods return intrusively ref-counted resource pointers (the `RHI<Name>Ptr` aliases, see below): `create_buffer(RHIBufferDesc)` (returns `RHIBufferPtr`), `create_texture`, `create_sampler`, `create_vertex_shader`, `create_pixel_shader`, `create_graphics_pipeline(RHIGraphicsPipelineDesc)`, `create_render_target`, `create_viewport(RHIViewportDesc)`; `submit(RHICommandList&)`, `present(RHIViewport&, RHITexture* source = nullptr)`, `capabilities()`. No bind-then-mutate state machine. Descriptors are data-only structs.
- **Intrusive reference counting for RHI resources (only):** every `RHI*` resource derives `RHIResource : RefCounted` (small atomic-count base) and is held through `Ref<T>`, with one alias per resource named `RHI<Name>Ptr` (`RHIBufferPtr`, `RHITexturePtr`, `RHISamplerPtr`, `RHIVertexShaderPtr`, `RHIPixelShaderPtr`, `RHIGraphicsPipelinePtr`, `RHIComputePipelinePtr`, `RHIRenderTargetPtr`, `RHIViewportPtr`, plus `RHIComputeShaderPtr` etc. when those classes appear; declared next to each class). Public RHI signatures and the wrappers use the aliases, never spell `Ref<...>` out. Both types are added to `Oryx/Memory` (minimal; `UniquePtr`/`SharedPtr` stay untouched and everything outside the RHI keeps using them). Why: (1) the GPU may still read a resource after the last C++ reference drops, so the final release goes through the virtual `RefCounted::on_last_release()` hook, which `RHIResource` overrides to push the object onto a process-wide retire queue private to `RHIResource.cpp`, destroying it once every device has completed the frame (plain delete is the default hook); `SharedPtr`'s separate record cannot be intercepted this way. (2) `RHICommandList` stores raw `RHI*` pointers while recording, and `IRHI::submit` takes real `Ref`s for the in-flight frames; a raw pointer can always become an owning `Ref` again. (3) Backend classes derive from the base (`MetalBuffer : RHIBuffer`), and Metal objects are themselves ref-counted, so lifetimes line up. The resource remembers its allocator, as `SharedPtr`'s record does, so the allocator module still applies. Cost: a second ownership type, justified only by the retire hook; record it in the decision log and the allocator doc. Wrappers in `Graphics/Resources` are engine-level objects held by `SharedPtr`/`UniquePtr` and hold the matching `RHI<Name>Ptr` internally.
- **Resource classes, all prefixed `RHI`:** `RHIBuffer`, `RHITexture`, `RHISampler`, `RHIPipeline`, `RHIRenderTarget`, `RHIViewport` are base classes (they hold their descriptor, no `I` prefix since they are not purely virtual); backends derive (`MetalBuffer`, ...). **Each shader stage is its own class:** `RHIShader` (common base: stage, entry point, `RHIShaderReflection`) with `RHIVertexShader` and `RHIPixelShader` now; `RHIComputeShader`, `RHITessControlShader`, `RHITessEvalShader` are added when first used, and the shape already admits them: `ShaderStage` is an abstract enum (`Vertex, Pixel, Compute, TessControl, TessEval`, backends map it, e.g. Metal has no hull/domain stage and implements tessellation as a compute kernel plus a post-tessellation vertex function), pipelines come in two kinds, `RHIGraphicsPipeline` (vertex [+ tess control + tess eval] + pixel, vertex layout, blend, target formats) and `RHIComputePipeline` (one compute shader), and `RHICommandList` gains `dispatch` alongside `draw`.
- **RHICommandList (yes, added):** a concrete, backend-neutral, recorded list of data-only commands: `begin_pass(RHIRenderTarget, clear)`, `set_pipeline`, `set_vertex_buffer`, `bind(BindingId, resource)`, `draw`, `end_pass`. Backends translate it at `IRHI::submit`. Why: `BatchRenderer2D` and the contract tests can assert on the recorded list with no GPU (and NullRHI becomes nearly trivial); the cost is one extra copy of small command structs per frame, which is irrelevant at 2D scale. Advanced users record a list themselves and submit to the same `IRHI`. If profiling ever shows a cost, direct per-backend encoding is a backend-internal change.
- **RHIViewport (the window-to-GPU surface), resolved without Core->RHI and without the RHI knowing `Window`:** `Window` (Core) exposes a plain-data `NativeWindowHandle` (opaque native pointer, logical size, framebuffer size, content scale). It knows nothing about RHI. `GraphicsLayer`, which already sits above both (Renderer depends on Core) and reads `Application::window()`, builds `RHIViewportDesc` from that handle and calls `IRHI::create_viewport(desc)`; on `WindowResizeEvent` it calls `viewport.resize()`. The RHI therefore sees only a desc, never a `Window`, and Core never sees RHI. `RHIViewport` owns the swapchain (Metal: `CAMetalLayer`) and vends the per-frame `RHIRenderTarget` (back buffer).
- **Renderer-level resource wrappers (thought through, not just the earlier examples).** Rule: a wrapper exists only if it adds engine-level meaning beyond the `RHI*` object, which already carries its descriptor. Verdict per type:
  - `Texture2D` (wraps `RHITexture`): **yes**. Adds size/format, a sampler choice, optional source `AssetHandle<Image>`, creation from `ImageAsset`.
  - `VertexBuffer`/`IndexBuffer`/`UniformBuffer` (wrap `RHIBuffer`): **yes, as typed buffers instead of one generic `Buffer`**. They add the vertex layout / index type / typed update (`set_data<T>`), the part users actually need, and avoid a vague `Buffer` name. No collision with existing `oryx::` types (checked).
  - `VertexShader`/`PixelShader` today, `ComputeShader`/`TessControlShader`/`TessEvalShader` when needed (deriving a thin `Shader` base; each wraps its `RHI*Shader`, one class per stage so a pipeline descriptor is stage-correct at compile time): **yes, but thin**: the RHI shader, its `RHIShaderReflection` and the entry point. Everything about *producing* a shader (source, compile, variants, caching) is the Shaders module's `ShaderProgram`, which owns the stage resources of each variant.
  - `Pipeline` (wraps `RHIPipeline`): **yes**. Owns its two shaders, vertex layout, blend/depth state and the `BindingId`s resolved once at creation; this is what `BatchRenderer2D` actually binds.
  - `RenderTarget` (wraps `RHIRenderTarget`): **yes**, holds its colour/depth `Texture2D` attachments so offscreen results can be sampled.
  - `Sampler`: **no wrapper**. `RHISampler` is just a descriptor object; `Texture2D` carries the sampling choice and a shared default sampler is cached by the renderer.
  - `RHIViewport`, `RHICommandList`: **no wrapper**. `GraphicsLayer`/`BatchRenderer2D` use them directly (the command list is already a neutral, engine-level type).
  Wrappers expose `rhi()` for advanced users; `Renderer`, `BatchRenderer2D` and `GpuAssetCache` speak only in wrappers; `RHICommandList` records the underlying RHI objects (as raw pointers while recording). Wrappers hold only their `RHI<Name>Ptr`, never a back-pointer to `IRHI`. 
- **Renderer** facade: static `Renderer::begin_scene/end_scene/flush/draw_triangle/draw_line/draw_quad/draw_rect/draw_sprite/draw_circle` (plus `submit` for hand-built `DrawItem`s; `draw_*` take `Texture2D`, not RHI types, and a `Camera` is the only per-scene input). It is the only static state; it forwards to one `RendererContext` (owns `UniquePtr<IRHI>`, `ShaderLibrary`, pipelines, `DefaultResources` and its `BatchRenderer2D`) created by `Renderer::init` and torn down through `register_shutdown_hook`. `BatchRenderer2D` is an ordinary instance class, constructed directly in tests. `Renderer::rhi()` returns `IRHI&` for advanced users; tools may also build their own batcher over their own `IRHI`. Facade-created resources are normal RHI objects so the two mix freely. See "Batching and the scene facade (Step 6)" below.
- **Window/Input and ownership:** `Application` owns the window as `UniquePtr<Window>` (null when headless; created on demand via `Application::create_window(WindowDesc)`, read via `window()`), not by value (the type is polymorphic, picked by `Window::create`, which selects the platform backend at compile time: MacOS/GLFW, else Null) and not by `GraphicsLayer`. Reasons: the window outlives every layer (the member is declared before the `LayerStack`, so layers detach and `GraphicsLayer` releases its `RHIViewport`/GPU resources first), several layers may need input without owning the window, and `Application` stays graphics-free (Core only). `Input` is a polled state object owned by the window (key/mouse down, pressed-this-frame, cursor in logical coordinates), fed by the same callbacks that post events through `Application::post_event`.
- **Application/LayerStack, one layer:** `Application` and `Layer` unchanged; a single `GraphicsLayer` (core-owned like `SimulationLayer`). Two layers are unnecessary because drawing is *queued*: game layers call `Renderer::draw_*` during their `update()` and nothing touches the GPU. `GraphicsLayer` is pushed as the last overlay, so its `update()` runs after them and does the whole frame: flush batches into an `RHICommandList`, acquire the back buffer (held for the shortest possible time), submit, present, then pump window events (delivered to layers next tick, same latency as polling at the start). Anything queued by a layer pushed after it simply lands in the next frame (documented, harmless one-frame lag). `GraphicsLayer::event` handles `WindowResizeEvent` (viewport resize); `GraphicsLayer::update` calls `Application::close()` when the window should close (`Application` itself turns a `WindowCloseEvent` into `close()`, which posts `ApplicationCloseEvent`). Failures throw `oryx::Error`; `LayerStack` disables the layer and Oasis exits non-zero as today.
- **Assets:** `AssetHandle<T>` = `{id, generation}` into a per-type table in `AssetManager` (instance owned by the app). Cached by path, ref-counted, with a `Loading/Ready/Failed` state so async/lazy loading arrives later without API change (synchronous first). `IAssetLoader<T>` registered by extension via a self-registering macro. CPU assets: `ImageAsset` (RGBA8), `FontAsset` (parsed TTF + glyph rasterise, no atlas), `ShaderAsset` (raw shader text + stage). `GpuAssetCache` maps an `AssetHandle<Image>` to its `Texture2D` on first use and releases it with the asset.
- **Shaders module and reflection:** `RHIShaderReflection` (attributes, bindings with slot/offset/size; data-only, in `Graphics/RHI`) is what backends fill and what `Shader` wrappers expose. `Shaders/` sits directly above `Graphics/` and uses its resources: `ShaderSource` (text, stage, entry point, defines), `ShaderReflection` (**Shaders' own type**: entry points, stage inputs/outputs, resource bindings with type and struct layout, compute thread-group size; richer than the RHI needs and free of RHI types), `IShaderCompiler` (MSL offline path, Slang later) returning `ShaderBinary` + `ShaderReflection` and never touching `IRHI`, `ShaderProgram`, and `ShaderLibrary`. **`ShaderProgram` is a set of stages, not a vertex/pixel pair:** a fixed array indexed by `ShaderStage`, each slot holding the matching resource wrapper (`VertexShader`, `PixelShader`, `ComputeShader`, `TessControlShader`, `TessEvalShader`, added with first use), a `ShaderProgramKind` (`Graphics` or `Compute`) that validates which stage combinations are legal (compute alone; vertex + pixel with optional tessellation pair), the per-backend binaries, and the seat for hot reload. Two reflection types, two jobs: the compiler's `ShaderReflection` describes the source; the created shader object's `RHIShaderReflection` (minimal, filled by the backend, e.g. from Metal's runtime reflection) is what the GPU object actually exposes. `ShaderProgram` converts and cross-checks them at creation (a mismatch is an `Error`), and `Pipeline` resolves `BindingId`s from the RHI one. `ShaderLibrary` (named/cached programs, including the built-in sprite/line/text shaders). `BatchRenderer2D` and `Pipeline` creation obtain shaders from `ShaderLibrary`. Each named binding resolves once at `Pipeline` creation to a `BindingId` (u32); `RHICommandList::bind` takes ids only (no string lookups in passes). MSL-first: embedded MSL compiled at startup by the Metal backend (`newLibraryWithSource`) and reflection read back from Metal; Slang later emits the same `RHIShaderReflection` offline.
- **DebugRenderer:** immediate-mode `line/rect/circle/text` over `BatchRenderer2D`, cleared each frame. Strategy visualisation consumes `Decision`/`Diagnostics` from `IDecisionObserver`; the Phase 11 dashboard builds on it with no new core hooks.
- **Math:** reuse `Vec2f`, `Mat3f`, `Colour`; add a tiny `Rect` only if three call sites need it.

## Open points

1. When a third backend or external backend appears, replace the `RHIBackend` switch with a registry.
2. Whether a `Layer::render()` phase is worth adding later (default: no core change; queued drawing makes it unnecessary).
3. HiDPI: `Input` reports logical coordinates, the RHI works in pixels; `Renderer` owns conversion.
4. Persistent asset identity (UUID): `AssetId` is a runtime slot index and the handle carries a generation, so stale handles are caught without one. A UUID (as in Hazel) is deferred until serialization or an asset registry needs identity across runs (open question §14). It must be deterministic (e.g. a hash of the normalised path or an id stored in asset metadata), not seeded from `std::random_device`, to respect `docs/design/determinism.md`.
5. Multiple windows / viewports (not built). Each `Window` already owns its own `PolledInput`, so a second window needs no `IInput` change. It would need: `Application` holding a window list plus a primary (today one `UniquePtr<Window>`); window identity on events (a window id or `Window*` on the `Event` base, since key/mouse/resize events currently carry none); screen-space cursor coordinates added to `IInput` for drags across viewports (cursor is per-window logical today). The static `Input` shortcut (`Input::key_down(...)`, Hazel-style, Core) forwards to the primary window only and reads as "nothing pressed" without a window.

## RHI contract rules (Step 3)

- `create_*`, `submit`, `present` and `acquire_back_buffer` run on the application thread; `Ref` copy and release are thread-safe from any thread.
- The device outlives every resource it created. Each device holds an `RHIDeviceLease` (the only retire-related line a backend writes); the last lease to go drains the queue and asserts no `RHIResource` is left. With no device alive a released resource is destroyed immediately.
- `submit` retains every referenced resource until the frame it was submitted in completes; `end_frame` is the frame boundary (`present` only encodes and commits presentation).
- Descriptor and update data is passed as `const uint8_t*` plus a size and is only read during the call.
- `NullRHI` renders nothing but stores buffer and texture bytes, applies clears to `R8Unorm`/`RGBA8Unorm`/`BGRA8Unorm` render targets and records `last_submission()`; other render target formats throw.
- `RHICommandList` is Unreal-style: commands derive from `RHICommand`, live in the list's arena as an intrusive linked list, and a backend consumes them through `IRHICommandContext` (`list.execute(context)`). Commands hold raw pointers and are trivially destructible; headless tests inspect a list by iterating it with `command_cast<T>`.
- Retention at record time: the list retains each resource when it records it (skipping the last resource per slot, then scanning the last 8 retained), so callers may drop their references before `submit`. `IRHI::submit(RHICommandList&)` consumes the list: its retained references move into the current frame slot and the list is cleared. Recording validates usage flags, offsets, vertex slot (< `RHI_MAX_VERTEX_SLOTS`) and pipeline/target colour format in O(1) from the compact resource state.
- Resources store compact state only (`RHIBuffer` size/usage/memory, `RHITexture` size/format/usage, `RHISampler` four enums, `RHIGraphicsPipeline` colour format/blend), never the creation desc, and no strings. `RHIPipeline` is an empty common base; shaders and attributes in `RHIGraphicsPipelineDesc` are read at creation and not retained. `ShaderStage` stays in `RHIShader.h` (`SHADER_STAGE_COUNT` sizes `ShaderProgram`'s stage array). `RHIShaderDesc::entry_point` is a creation-time `const char*`: `ShaderProgram` owns the entry point text.
- Buffer sizes and offsets are `uint32_t`: a buffer is limited to 4 GiB. Frames in flight are device state (`RHICapabilities`), not a viewport option. A resource belongs to the device that created it; mixing devices is undefined (no per-object device id).
- The retire queue is global and private to `RHIResource.cpp`; entries carry the global frame serial and are popped as a prefix. An entry is freed only when its serial is <= the minimum completed serial over all live leases (`RHIDeviceLease::complete(serial)`); an idle lease (`set_idle()`) counts as complete, so any number of devices coexist safely with no per-object device id or retirer pointer (`RefCounted` is 32 bytes).
- `IRHI::present(viewport, source)`: a non-null `source` is copied into the back buffer first and must be `Sampled` with the viewport's size and format (`rhi_validate_present_source`, shared by backends). `NullRHI` keeps a ring of `frames_in_flight` reusable slots: `present` clears the current slot, advances and completes the frame; `wait_idle` clears every slot and completes.
- `RHIViewportDesc` carries an opaque `void* native_window` plus pixel size and scale, never a window type; the caller fills it from `NativeWindowHandle`. Only buffers and textures take a creation-time debug `name` (`const char*`, not stored).

## Metal and Renderer (Step 4)

- The RHI owns resource mutation, as in Unreal: `IRHI::resize_viewport(viewport, w, h, scale)` replaces a viewport-side resize; `RHIViewport` is read-only (`width/height/format/acquire_back_buffer`).
- Frame pacing is a ring of `frames_in_flight` (3) frames owned by `MetalCommandQueue`; `end_frame` blocks with `waitUntilCompleted` on the oldest frame (polling, never a semaphore), and failures throw on the application thread. No semaphores, mutexes or completion handlers.
- A null `RHIViewportDesc::native_window` gives an offscreen viewport so the shared contract runs headless; a real window gets a child `NSView` hosting a `CAMetalLayer`.
- `Renderer` (static facade) owns the device, the clear colour and the per-frame `DrawItem` queue; `GraphicsLayer` owns the viewport and the frame (see Step 5).
- Manual check: `Oasis --playground --rhi=metal` (also with `MTL_DEBUG_LAYER=1`); `--rhi=null` draws nothing.

## RHI contract v2 and the Step 5 frame (Step 5)

- **Binding-layout model.** A pipeline is created with a binding layout (`bindings` + `binding_count` in `RHIGraphicsPipelineDesc`): an array of `RHIBindingDesc { kind, stage_mask, data_type, texture_dimension, slot, array_count, size }`. There are no names. `RHIBindingId` is an index into that table and is what every bind call takes (`bind_buffer`, `bind_texture(id, texture, array_index)`, `bind_sampler`, `set_constants(id, data, size)`). `RHICommandList` validates each call against the current pipeline's table (id in range, kind, constants size, array index, texture dimension, sampled usage, data type), so mistakes throw at record time, not in the driver.
- **Why the RHI does not reflect.** Reflection is a property of shader source, so it lives once, in `Shaders/` (`ShaderReflection`, `ShaderParameterMap`). `Shaders/ShaderBindings` turns it into the RHI layout (vertex and pixel merged, stage masks unioned); `Pipeline` keeps the name to `RHIBindingId` table. `RHIShader` holds only stage, entry point and code, so no second description can drift. In debug builds the Metal backend cross-checks the layout against Metal's own binding info and vertex attributes.
- **Constants and buffers.** `set_constants` copies up to 4096 bytes into the list arena and maps to `setVertexBytes`/`setFragmentBytes`, so per-batch camera data needs no uniform ring. `VertexBuffer`/`IndexBuffer` in `Dynamic` mode hold `frames_in_flight` regions in one CpuToGpu buffer; callers write `Renderer::frame_slot()`'s region and bind its `offset()`. The queue blocks on the oldest frame in `end_frame`, so an in-flight region is never overwritten.
- **`present` / `end_frame` split.** `IRHI::present(viewport, source)` only encodes and commits presentation. `IRHI::end_frame()` advances the frame ring and serial, once per frame, after `present` (or alone when nothing was presented). `Renderer::end_frame` does both, in that order.
- **Metal argument-table conventions.** Vertex streams bind at `METAL_VERTEX_STREAM_BASE + slot` (base 16) so they never collide with buffer bindings `0..15`. Each binding maps to a per-stage Metal index (`slot` plus `array_index` for texture arrays); an `array<texture2d<float>, N>` needs every element bound, so batches fill unused elements with a 1x1 white texture.
- **Who owns the frame.** `GraphicsLayer` (pushed last) owns the viewport and the clear colour and calls `Renderer::end_frame`; other layers never touch the pass. Layers hand the renderer data: `Renderer::submit(const DrawItem&)` queues one draw (pipeline, vertex/index buffers, inline constants, textures and sampler; the Unreal `FMeshBatch` analogue). `end_frame` acquires the back buffer, records `begin_pass`, `record_draw_item` for each item in order, `end_pass`, then `submit`, `present`, `end_frame`. `BatchRenderer2D` (Step 6) will batch into `DrawItem`s, and sorting by state or extra passes can be added inside `end_frame` without changing layers. Items submitted after `GraphicsLayer` ran land in the next frame.
- **Corrections (F8).** The Metal queue polls and retires finished frames and waits with `waitUntilCompleted`; it uses no semaphore or completion handlers, and the layer sets `framebufferOnly = false`.
- **Playground.** `Oasis --playground` is the test bed. Since Step 6 it draws through `Renderer::begin_scene/draw_*/end_scene` (a rotating triangle, a line fan, a checker sprite plus a flat rect, an animated SDF circle) with no buffers or pipelines of its own. `--rhi=null` runs the same path and draws nothing.

## Batching and the scene facade (Step 6)

- **Two layers, one rule.** `BatchRenderer` (base) accumulates transient primitives and turns each run of identical state into one `DrawItem` pushed to an injected `std::vector<DrawItem>&` sink, in submission order. `BatchRenderer2D` (derived) is only the primitive API: it registers one stream per `Primitive2D` from `primitive_traits()` and writes `Vertex2D*` vertices. Neither the base nor any batcher touches RHI commands; `GraphicsLayer` records the sink.
- **Streams.** A `BatchStreamDesc` (vertex size, vertices and indices per primitive, textured, `BuiltinPipeline`) is one row; a derived class adds rows with `register_stream`, so a 3D or glyph batcher reuses all of the machinery. Indexed streams are quads (4 vertices, 6 indices) drawn from the shared static `DefaultResources::quad_indices` (U16, `QUAD_INDEX_MAX_QUADS` per draw); lines and triangles are non-indexed. A primitive is added as `select` (stream and sampler) then `acquire_texture` (textured streams) then `append`; only the first two can flush, so a slot index never goes stale.
- **State tracking and flush rules.** The batch key is `{stream, sampler}` (the pipeline follows from the stream; blend is baked into it). A change flushes the open batch with a counted `FlushReason`: `StreamChange`, `SamplerChange`, `TextureSlotsFull`, `IndexLimit` (the per-draw quad cap), plus `Explicit` (`flush`) and `End`. Only consecutive draws with identical state merge, so submission order is the batching contract; there is no sorting inside the batcher.
- **Storage.** Vertices are staged on the CPU per batch. A flush copies them into a `TransientAllocator` page (one persistently mapped upload buffer per page, one region per frame in flight; pages are 4 MiB, a larger request gets its own page, and pages persist, so a steady frame allocates nothing) and the `DrawItem` binds that buffer at a byte `vertex_offsets[0]`. Queued items keep the page alive. `recycle(frame_slot)` rewinds the pages; the owner calls it when a slot's frame begins (`record_frame` does it right after `end_frame`), never between scenes of one frame, so several scenes can share a frame.
- **Texture slots.** `TextureSlotTable` maps textures to slots in one batch: slot 0 is the white default, repeats reuse their slot, and a full table flushes. The count is `QuadPS::texture_count(permutation)`; `RHI_MAX_TEXTURE_BINDINGS` (32) is the compile-time ceiling shared by `DrawItem`, `QuadPS` and the table, and the batcher picks the 32-slot permutation only when `RHICapabilities::max_texture_bindings` allows it, else 16.
- **Camera and constants.** `Camera` (projection and view `Mat4f`) is the only per-scene input, so 2D and 3D share `begin(const Camera&)`. Each draw carries `BatchConstants { view_projection }` (column-major) as inline constants.
- **Facade rules.** `begin_scene` inside a scene, `draw_*`/`end_scene`/`flush` outside one, and `end_frame` with a scene still open throw `Error`. Coordinates are world units in a **left-handed** system (+x right, +y up, +z into the screen; `Mat4f` view space looks down +Z, `look_at`, `orthographic` and `perspective` follow it, clip depth is [0, 1]); a primitive's position is its centre and rotation is counter-clockwise radians about it; a sprite's uv rectangle runs from its top-left to its bottom-right corner.

### BatchRenderer and SceneRenderer: siblings, not a hierarchy

`SceneRenderer` is not built; the decision is recorded so Step 6 leaves the seams for it. It follows Unreal's split between dynamic primitives (`FSimpleElementCollector`, batched elements) and `FSceneRenderer` (views, passes, visibility, mesh batches).

| | `BatchRenderer` | `SceneRenderer` (future) |
|---|---|---|
| Role | immediate-style accumulator for dynamic, transient 2D/3D primitives (UI, gizmos, debug, procedural shapes) | orchestrator of views and passes for 2D and 3D scenes: pass ordering, sorting, culling, sprite and mesh batches, material state; no mandatory scene graph |
| Input | `draw_*` calls between `begin(camera)` and `end()` | a flat set of submitted renderables per view |
| Output | `DrawItem`s into a sink | `DrawItem`s into per-pass lists |

- **No inheritance.** `SceneRenderer` does not derive from `BatchRenderer`: it is not a kind of accumulator, and inheriting would drag primitive state into view/pass logic. **Composition instead:** a `SceneRenderer` owns one `BatchRenderer2D` (or 3D) per pass that needs dynamic primitives, next to sibling emitters such as a future `MeshRenderer`; all of them write `DrawItem`s into lists the scene provides, and `RendererContext` records the lists.
- **Immediate path stays.** `Renderer::begin_scene/draw_*` is the context's default batcher writing into the back-buffer list, for debug draw, UI and simple games such as Tic-Tac-Toe; a game adopts `SceneRenderer` only when it needs views or passes and may use both.
- **Seams Step 6 provides:** the sink is injected and the camera is a parameter (a scene hands each pass its own list and camera); batchers register in `RendererContext::batchers` so scene-owned ones are recycled once per frame; sorting and culling live outside the batcher; the camera base class carries 2D and 3D alike. Deferred until a consumer exists: a render-pass list in `record_frame` (offscreen targets), a `DrawItem` sort key, a scissor rectangle on the batch key and `DrawItem` (needed by the Phase 11 dashboard), instanced quads, a custom-pipeline hook on a stream (SDF text, materials), and a `draw_sprite(AssetHandle<ImageAsset>)` overload (the `Application` owns no `AssetManager` yet).
