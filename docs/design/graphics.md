## Module layout and layering

Public API in `Oryx/src/Oryx/`, namespace `oryx`:

             RHICommandList, RHIShaderReflection) and Resources/ (GPU resource wrappers, each owns its RHI

GLFW lives in `Oryx/vendor/glfw`, used by the desktop platform backends. Vendors: `glfw`, `stb`. Oasis has no graphics code: its games register presenters (`Oasis/src/Oasis/Game/*Presenter`), drawn by `Board/Graphics/`.

**Dependency rules (reviewed, plus grep/link checks in CI):**
- `Core/Window.h`, `Core/Input.h`, window/input events and `Assets` (CPU) are always compiled and depend on nothing graphical; they work headless (a `Window` request with no backend resolves to NullWindow or throws a clear `Error`).
- **Strictly linear layering, enforced by include checks:** `Graphics/` -> `Shaders/` -> `Renderer/` -> `Interface/Canvas/` -> `Interface/UI/` -> `Board/Graphics/`. Each layer may include only itself, the layers below it, `Core`, `Math` and CPU `Assets`; none may include a layer above. This replaces the earlier "Renderer sandwiched around Shaders" arrangement. RHI types appear in `Renderer/` only via `Renderer::rhi()` and the resource wrappers' `rhi()` accessors.
- **Hard rule: Graphics/, Shaders/ and Renderer/ never include, name or depend on Assets/.** They are standalone and take plain data or their own interfaces. The only Assets -> Graphics edge is `Assets/GpuAssetCache`, which produces `Texture2D` wrappers; CPU asset headers never include it. Shaders are not assets today (see [ShaderAsset](#shaderasset-decision-and-seam)). Fonts follow the same shape: the headless `Text/` module owns the glyph data (`GlyphAtlasData`), layout (`layout_text`) and the `IFontSource` interface; `Assets/AssetFontSource` implements it from a `FontAsset` (baking and caching live in `Assets/GlyphAtlasBaker`); `Renderer/Font` and `GlyphAtlas` see only `IFontSource`/`GlyphAtlasData`. `forge boundaries check` fails the build on any Graphics/Shaders/Renderer/Text include of Assets.
- `Graphics/`, `Shaders/` and `Renderer/` are graphics-option only. Compilers shell out to `xcrun metal`/`slangc` and throw a clear `Error` when absent.
- `backends/Metal` and `backends/MacOS` do not include each other; they meet only through `NativeWindowHandle` (Core).
- `Game/`, `Strategy/`, `Simulation/` never include Graphics, Shaders, Renderer or Window. Public headers never include `backends/`.

## Core abstractions

```
File -> AssetManager/Importer (+ CompiledAssetStore) -> CPU Asset (headless-safe)
                                  | GpuAssetCache (graphics only)
                               IRHI -> RHI resources
Window(Core) --events--> Application/LayerStack ; Input polled from Window
  game layers: Renderer facade / DebugRenderer -> batched by BatchRenderer2D into DrawItems (no RHI commands until GraphicsLayer records the frame)
GraphicsLayer (single overlay, pushed last): flush -> RHICommandList -> acquire back buffer -> submit -> present
                                             -> pump window events      [glue: sees Window + IRHI]
```

- **IRHI** (pure virtual, one instance per backend, owned, never global): the device, chosen by `create_rhi(RHIBackend)`, a plain enum (`Null`, `Metal`; `OpenGL` etc. added when built) and a `switch` guarded by per-backend defines. There is no registry. This is a deliberate, recorded deviation from the self-registering principle (decision log) until a third backend or an external backend justifies one. Factory methods return intrusively ref-counted resource pointers (the `RHI<Name>Ptr` aliases, see below): `create_buffer(RHIBufferDesc)` (returns `RHIBufferPtr`), `create_texture`, `create_sampler`, `create_vertex_shader`, `create_pixel_shader`, `create_graphics_pipeline(RHIGraphicsPipelineDesc)`, `create_render_target`, `create_viewport(RHIViewportDesc)`; `submit(RHICommandList&)`, `present(RHIViewport&, RHITexture* source = nullptr)`, `capabilities()`. No bind-then-mutate state machine. Descriptors are data-only structs.
- **Intrusive reference counting for RHI resources (only):** every `RHI*` resource derives `RHIResource : RefCounted` (small atomic-count base) and is held through `Ref<T>`, with one alias per resource named `RHI<Name>Ptr` (`RHIBufferPtr`, `RHITexturePtr`, `RHISamplerPtr`, `RHIVertexShaderPtr`, `RHIPixelShaderPtr`, `RHIGraphicsPipelinePtr`, `RHIComputePipelinePtr`, `RHIRenderTargetPtr`, `RHIViewportPtr`, plus `RHIComputeShaderPtr` etc. when those classes appear; declared next to each class). Public RHI signatures and the wrappers use the aliases, never spell `Ref<...>` out. Both types are added to `Oryx/Memory` (minimal; `UniquePtr`/`SharedPtr` stay untouched and everything outside the RHI keeps using them). Why: (1) the GPU may still read a resource after the last C++ reference drops, so the final release goes through the virtual `RefCounted::on_last_release()` hook, which `RHIResource` overrides to push the object onto a process-wide retire queue private to `RHIResource.cpp`, destroying it once every device has completed the frame (plain delete is the default hook); `SharedPtr`'s separate record cannot be intercepted this way. (2) `RHICommandList` stores raw `RHI*` pointers while recording, and `IRHI::submit` takes real `Ref`s for the in-flight frames; a raw pointer can always become an owning `Ref` again. (3) Backend classes derive from the base (`MetalBuffer : RHIBuffer`), and Metal objects are themselves ref-counted, so lifetimes line up. The resource remembers its allocator, as `SharedPtr`'s record does, so the allocator module still applies. Cost: a second ownership type, justified only by the retire hook; record it in the decision log and the allocator doc. Wrappers in `Graphics/Resources` are engine-level objects held by `SharedPtr`/`UniquePtr` and hold the matching `RHI<Name>Ptr` internally.
- **Resource classes, all prefixed `RHI`:** `RHIBuffer`, `RHITexture`, `RHISampler`, `RHIPipeline`, `RHIRenderTarget`, `RHIViewport` are base classes (they hold their descriptor, no `I` prefix since they are not purely virtual); backends derive (`MetalBuffer`, ...). **Each shader stage is its own class:** `RHIShader` (common base: stage, entry point, `RHIShaderReflection`) with `RHIVertexShader` and `RHIPixelShader` now; `RHIComputeShader`, `RHITessControlShader`, `RHITessEvalShader` are added when first used, and the shape already admits them: `ShaderStage` is an abstract enum (`Vertex, Pixel, Compute, TessControl, TessEval`, backends map it, e.g. Metal has no hull/domain stage and implements tessellation as a compute kernel plus a post-tessellation vertex function), pipelines come in two kinds, `RHIGraphicsPipeline` (vertex [+ tess control + tess eval] + pixel, vertex layout, blend, target formats) and `RHIComputePipeline` (one compute shader), and `RHICommandList` gains `dispatch` alongside `draw`.
- **RHICommandList (yes, added):** a concrete, backend-neutral, recorded list of data-only commands: `begin_pass(RHIRenderTarget, clear)`, `set_pipeline`, `set_vertex_buffer`, `bind(BindingId, resource)`, `draw`, `end_pass`. Backends translate it at `IRHI::submit`. Why: `BatchRenderer2D` and the contract tests can assert on the recorded list with no GPU (and NullRHI becomes nearly trivial); the cost is one extra copy of small command structs per frame, which is irrelevant at 2D scale. Advanced users record a list themselves and submit to the same `IRHI`. If profiling ever shows a cost, direct per-backend encoding is a backend-internal change.
- **RHIViewport (the window-to-GPU surface), resolved without Core->RHI and without the RHI knowing `Window`:** `Window` (Core) exposes a plain-data `NativeWindowHandle` (opaque native pointer, logical size, framebuffer size, content scale). It knows nothing about RHI. `GraphicsLayer`, which already sits above both (Renderer depends on Core) and reads `Application::window()`, builds `RHIViewportDesc` from that handle and calls `IRHI::create_viewport(desc)`; on `WindowResizeEvent` it calls `viewport.resize()`. The RHI therefore sees only a desc, never a `Window`, and Core never sees RHI. `RHIViewport` owns the swapchain (Metal: `CAMetalLayer`) and vends the per-frame `RHIRenderTarget` (back buffer).
- **Renderer-level resource wrappers (thought through, not just the earlier examples).** Rule: a wrapper exists only if it adds engine-level meaning beyond the `RHI*` object, which already carries its descriptor. Verdict per type:
  - `Texture2D` (wraps `RHITexture`): **yes**. Adds size/format, a sampler choice, optional source `AssetHandle<Image>`, creation from `ImageAsset`.
  - `VertexBuffer`/`IndexBuffer`/`UniformBuffer` (wrap `RHIBuffer`): **yes, as typed buffers instead of one generic `Buffer`**. They add the vertex layout / index type / typed update (`set_data<T>`), the part users actually need, and avoid a vague `Buffer` name. No collision with existing `oryx::` types (checked).
  - `VertexShader`/`PixelShader` today, `ComputeShader`/`TessControlShader`/`TessEvalShader` when needed (deriving a thin `Shader` base; each wraps its `RHI*Shader`, one class per stage so a pipeline descriptor is stage-correct at compile time): **yes, but thin**: the RHI shader, its `RHIShaderReflection` and the entry point. Everything about *producing* a shader (source, compile, variants, caching) is the Shaders module's `ShaderProgram`, which owns the stage resources of each variant.
  - `Pipeline` (wraps `RHIPipeline`): **yes**. Owns its two shaders, vertex layout, blend/depth state and the `BindingId`s resolved once at creation; this is what `BatchRenderer2D` actually binds.
  - `RenderTarget` (wraps `RHIRenderTarget`): **yes**, holds its colour/depth `Texture2D` attachments so offscreen results can be sampled.
  - `Sampler`: **no wrapper**. `RHISampler` is just a descriptor object; `Texture2D` carries the sampling choice and a shared default sampler is cached by the renderer.
  - `RHIViewport`, `RHICommandList`: **no wrapper**. `GraphicsLayer`/`BatchRenderer2D` use them directly (the command list is already a neutral, engine-level type).
  Wrappers expose `rhi()` for advanced users; `Renderer`, `BatchRenderer2D` and `GpuAssetCache` speak only in wrappers; `RHICommandList` records the underlying RHI objects (as raw pointers while recording). Wrappers hold only their `RHI<Name>Ptr`, never a back-pointer to `IRHI`. 
- **Renderer** facade: static `Renderer::scene()` (the frame's `SceneRenderer`: `begin_scene`, `submit` a `RenderSource`, `end_scene`), `submit` for hand-built `DrawItem`s, and the RHI/pipeline/shader accessors; 2D primitives are drawn by `BatchRenderer2D` inside a scene stage (`draw_*` take `Texture2D`, not RHI types, and a `Camera` is the only per-view input). It is the only static state; it forwards to one `RendererContext` (owns `UniquePtr<IRHI>`, `ShaderLibrary`, pipelines, `DefaultResources` and its `SceneRenderer`, which owns the `BatchRenderer2D` and the pass list) created by `Renderer::init` and torn down through `register_shutdown_hook`. `BatchRenderer2D` is an ordinary instance class, constructed directly in tests. `Renderer::rhi()` returns `IRHI&` for advanced users; tools may also build their own batcher over their own `IRHI`. Facade-created resources are normal RHI objects so the two mix freely. See "Batching and the scene facade (Step 6)" below.
- **Window/Input and ownership:** `Application` owns the window as `UniquePtr<Window>` (null when headless; created on demand via `Application::create_window(WindowDesc)`, read via `window()`), not by value (the type is polymorphic, picked by `Window::create`, which selects the platform backend at compile time: MacOS/GLFW, else Null) and not by `GraphicsLayer`. Reasons: the window outlives every layer (the member is declared before the `LayerStack`, so layers detach and `GraphicsLayer` releases its `RHIViewport`/GPU resources first), several layers may need input without owning the window, and `Application` stays graphics-free (Core only). `Input` is a polled state object owned by the window (key/mouse down, pressed-this-frame, cursor in logical coordinates), fed by the same callbacks that post events through `Application::post_event`.
- **Application/LayerStack, one layer:** `Application` and `Layer` unchanged; a single `GraphicsLayer` (core-owned like `SimulationLayer`). Two layers are unnecessary because drawing is *queued*: game layers call `Renderer::draw_*` during their `update()` and nothing touches the GPU. `GraphicsLayer` is pushed as the last overlay, so its `update()` runs after them and does the whole frame: flush batches into an `RHICommandList`, acquire the back buffer (held for the shortest possible time), submit, present, then pump window events (delivered to layers next tick, same latency as polling at the start). Anything queued by a layer pushed after it simply lands in the next frame (documented, harmless one-frame lag). `GraphicsLayer::event` handles `WindowResizeEvent` (viewport resize); `GraphicsLayer::update` calls `Application::close()` when the window should close (`Application` itself turns a `WindowCloseEvent` into `close()`, which posts `ApplicationCloseEvent`). Failures throw `oryx::Error`; `LayerStack` disables the layer and Oasis exits non-zero as today.
- **Assets:** `AssetHandle<T>` = `{id, generation}` into a per-type table in `AssetManager`; `Assets::manager()` is the lazily created global instance (`Assets::use<Sub>()` swaps in a subclass) and `Assets::update()` is ticked by `Application::run`. Cached by path, ref-counted, `load` returns a `Loading` handle and a queued request settles on `update()` (`DeferredExecutor`, no threads yet; `AssetSettings::worker_threads > 0` throws). Reload bumps `revision`, not `generation`. One `IAssetImporter<T>` per extension (`import_source` is pure and compiled on disk by content hash into `CompiledAssetStore`; `instantiate` builds the runtime asset). Every asset derives `Asset`. CPU assets: `ImageAsset` (RGBA8), `FontAsset` (parsed TTF + glyph rasterise, no atlas); there is no `ShaderAsset`. `GpuAssetCache` maps an `AssetHandle<Image>` to its `Texture2D` on first use and releases it with the asset.
- **Permutations and pipeline state.** Following Unreal, what is intrinsic to a shader lives with its class and what is pass state lives in the pass. A shader's permutations are a domain type (`ShaderPermutationDomain<Dimension>`, `Shaders/ShaderPermutation.h`) given to `StaticShader`/`BuiltinShader` as a template argument; `defines_for`/`should_compile` remain the overridable hooks and default to the domain. Topology, blend, the VS+PS pair and the vertex declaration are a `PipelineDef` (`Renderer/PipelineDef.h`) that the pass owns, e.g. `pipeline_def(Primitive2D)`; `Shaders/` never sees them. A pass picks the permutation from a device capability through the domain (`fitting`).
- **Shaders module and reflection:** `RHIShaderReflection` (attributes, bindings with slot/offset/size; data-only, in `Graphics/RHI`) is what backends fill and what `Shader` wrappers expose. `Shaders/` sits directly above `Graphics/` and uses its resources: `ShaderSource` (text, stage, entry point, defines), `ShaderReflection` (**Shaders' own type**: entry points, stage inputs/outputs, resource bindings with type and struct layout, compute thread-group size; richer than the RHI needs and free of RHI types), `IShaderCompiler` (MSL offline path, Slang later) returning `ShaderBinary` + `ShaderReflection` and never touching `IRHI`, `ShaderProgram`, and `ShaderLibrary`. **`ShaderProgram` is a set of stages, not a vertex/pixel pair:** a fixed array indexed by `ShaderStage`, each slot holding the matching resource wrapper (`VertexShader`, `PixelShader`, `ComputeShader`, `TessControlShader`, `TessEvalShader`, added with first use), a `ShaderProgramKind` (`Graphics` or `Compute`) that validates which stage combinations are legal (compute alone; vertex + pixel with optional tessellation pair), the per-backend binaries, and the seat for hot reload. The compiler's `ShaderReflection` is the single source of truth (persisted with the compiled output; there is no second, backend-filled reflection type). The Metal backend cross-checks it at pipeline creation against `MTLRenderPipelineReflection` and `MTLFunction::vertexAttributes` (see [Runtime reflection cross-check](#runtime-reflection-cross-check)), and `Pipeline` resolves `BindingId`s from the merged layout. `ShaderLibrary` (named/cached programs, including the built-in sprite/line/text shaders). `BatchRenderer2D` and `Pipeline` creation obtain shaders from `ShaderLibrary`. Each named binding resolves once at `Pipeline` creation to a `BindingId` (u32); `RHICommandList::bind` takes ids only (no string lookups in passes). MSL-first: embedded MSL compiled at startup by the Metal backend (`newLibraryWithSource`) and reflection read back from Metal; Slang later emits the same `RHIShaderReflection` offline.
- **DebugRenderer:** immediate-mode `line/rect/circle/text` over `BatchRenderer2D`, cleared each frame. Strategy visualisation consumes `Decision`/`Diagnostics` from `IDecisionObserver`; the Phase 11 dashboard builds on it with no new core hooks.
- **Math:** reuse `Vec2f`, `Mat3f`, `Colour`; add a tiny `Rect` only if three call sites need it.

## Build and dependency integration

- **forge.toml:** `[options] graphics = { default = true, off = "--no-graphics", help = "Window backends, RHI and 2D renderer" }`; `[dependencies] glfw = { kind = "static", requires = ["graphics"], ... }`; `stb` header-only with **no** `requires` (CPU assets need it headless). Toggling the option wipes `bin`/`bin-int` like `--without python`.
- **Premake:** `premake/graphics.lua` (pattern of `python.lua`, `graphicsEnabled()`). `Oryx/premake5.lua` conditionally adds `src/Oryx/{Graphics,Shaders,Renderer}` (incl. `Graphics/RHI`, `Graphics/Resources`), `src/Oryx/Assets/GpuAssetCache*` and `backends/Null`; `system:macosx` adds `backends/Metal` (`.mm`, `NoPCH`, `-fobjc-arc`, frameworks Metal/QuartzCore/Foundation) and `backends/MacOS` (`.mm`, GLFW, frameworks AppKit/IOKit/Cocoa). Core's `Window`/`Input` and event headers are unconditional. Oasis adds its `Graphics/` folder under the same flag. `forge.whole_archive` keeps backend static registrars linked.
- **Linux/CI:** with graphics on, Linux builds the Graphics/Shaders/Renderer modules with Null backends only (no GLFW/X11 packages), so the API and `BatchRenderer2D` are exercised in CI. Add a graphics-off leg and a check that a graphics-off `Oryx` contains no Graphics/Shaders/Renderer symbols.
- **Slang (milestone 9):** `slangc` is a `kind = "tool"` archive dependency with per-platform url/sha256 (`[dependencies.slang.platforms.<os>-<arch>]`), fetched into the shared cache only when `graphics` is on; Premake passes its path to `SlangCompiler.cpp` as `OX_SLANGC_PATH`.

## Open points

1. When a third backend or external backend appears, replace the `RHIBackend` switch with a registry.
2. Whether a `Layer::render()` phase is worth adding later (default: no core change; queued drawing makes it unnecessary).
3. HiDPI: `Input` reports logical coordinates, the RHI works in pixels; `Renderer` owns conversion.
4. Persistent asset identity (UUID): `AssetId` is a runtime slot index and the handle carries a generation, so stale handles are caught without one. A UUID (as in Hazel) is deferred until serialization or an asset registry needs identity across runs (open question §14). It must be deterministic (e.g. a hash of the normalised path or an id stored in asset metadata), not seeded from `std::random_device`, to respect `docs/design/determinism.md`.
5. Multiple windows / viewports (not built). Each `Window` already owns its own `PolledInput`, so a second window needs no `IInput` change. It would need: `Application` holding a window list plus a primary (today one `UniquePtr<Window>`); window identity on events (a window id or `Window*` on the `Event` base, since key/mouse/resize events currently carry none); screen-space cursor coordinates added to `IInput` for drags across viewports (cursor is per-window logical today). The static `Input` shortcut (`Input::key_down(...)`, Hazel-style, Core) forwards to the primary window only and reads as "nothing pressed" without a window.

## RHI contract rules (Step 3)

- `create_*`, `submit`, `present` and `acquire_back_buffer` run on the application thread; `Ref` copy and release are thread-safe from any thread.
- The device outlives every resource it created. Each device holds an `RHIDeviceLease` (the only retire-related line a backend writes); the last lease to go drains the queue and asserts no `RHIResource` is left. With no device alive a released resource is destroyed immediately.
- `submit` retains every referenced resource until the frame it was submitted in completes; `end_frame` is the frame boundary (`present` only encodes and commits presentation).
- Descriptor and update data is passed as `const uint8_t*` plus a size and is only read during the call.
- `NullRHI` renders nothing but stores buffer and texture bytes, applies clears to `R8Unorm`/`RGBA8Unorm`/`BGRA8Unorm` render targets and records `last_submission()`; other render target formats throw.
- `RHICommandList` is Unreal-style and split like `FRHICommandListBase`/`FRHICommandList`: commands derive from `RHICommandT<Derived>` (CRTP: `NAME`, `run(IRHICommandContext&)`, type id and `command_name()` come from the base, so there is no type enum), live in an `RHICommandStream` (arena plus intrusive chain), and a backend consumes them through `IRHICommandContext` (`list.execute(context)`, which adds `command #N <Name>` to a plain `Error`). Commands hold raw pointers and are trivially destructible; headless tests inspect a list by iterating it with `command_cast<T>` or comparing `command_name()`. `NullRHI::last_submission()` is the list of command names. The private helpers (`RHICommandListBase`, `RHICommandStream`, `RHIResourceRetainer`, `RHIValidationContext`) live in `Graphics/RHI/Detail/`; only `RHICommandList`, the command structs and `RHIDebugScope` are public.
- Retention at record time: the list retains each resource when it records it (skipping the last resource per slot, then scanning the last 16 retained (`RHIResourceRetainer`)), so callers may drop their references before `submit`. `IRHI::submit(RHICommandList&)` consumes the list: its retained references move into the current frame slot and the list is cleared. Recording validates usage flags, offsets, vertex slot (< `RHI_MAX_VERTEX_SLOTS`) and pipeline/target colour format in O(1) from the compact resource state.
- Validation is a decorator, not list code: `RHIValidationContext : IRHICommandContext` tracks the pass, pipeline, bound resources and debug groups and throws on a mistake. The list owns one without an inner context so errors still throw at the recording call; with an inner context it wraps a backend context to check a hand-built or replayed stream. A draw needs every binding of the pipeline (each array element) and every vertex slot its attributes read (`RHIGraphicsPipeline::vertex_slot_mask`) bound since the last `set_pipeline`, and `draw_indexed` needs its index range inside the bound index buffer; both reset at `end_pass`. Vertex-buffer ranges are not checked (the pipeline keeps no strides). Binding arrays are capped at 32 elements so the per-element bound mask fits a word.
- Breadcrumbs: `RHIDebugScope` is RAII over `push_debug_group`/`pop_debug_group` (it skips the pop while unwinding). The validation context keeps the open group names (16 named levels) and prefixes errors with them: `RHI validation [Frame > BackBuffer Pass]: ... in draw`. `record_frame` brackets the frame and the back-buffer pass, and appends `[Draw Batch n]` to a failing item's error. A draw item without constants on a pipeline with a frame binding gets zero constants, like the default texture and sampler.
- Buffer sizes: `checked_buffer_bytes(capacity, stride, regions)` throws `Error` instead of wrapping past 4 GiB (used by `TransientAllocator`, `VertexBuffer`, `IndexBuffer`, `UniformBuffer`). `UniformBuffer` has one 256-byte-aligned region per frame in flight (`set_data(frame_slot, value)`, `offset(frame_slot)`); per-frame appends go through `TransientAllocator`, not a second cursor on `VertexBuffer`.
- Resources store compact state only (`RHIBuffer` size/usage/memory, `RHITexture` size/format/usage, `RHISampler` four enums, `RHIGraphicsPipeline` colour format/blend), never the creation desc, and no strings. `RHIPipeline` is an empty common base; shaders and attributes in `RHIGraphicsPipelineDesc` are read at creation and not retained. `ShaderStage` stays in `RHIShader.h` (`SHADER_STAGE_COUNT` sizes `ShaderProgram`'s stage array). `RHIShaderDesc::entry_point` is a creation-time `const char*`: `ShaderProgram` owns the entry point text.
- Buffer sizes and offsets are `uint32_t`: a buffer is limited to 4 GiB. Frames in flight are device state (`RHICapabilities`), not a viewport option. A resource belongs to the device that created it; mixing devices is undefined (no per-object device id).
- The retire queue is global and private to `RHIResource.cpp`; entries carry the global frame serial and are popped as a prefix. An entry is freed only when its serial is <= the minimum completed serial over all live leases (`RHIDeviceLease::complete(serial)`); an idle lease (`set_idle()`) counts as complete, so any number of devices coexist safely with no per-object device id or retirer pointer (`RefCounted` is 32 bytes).
- `IRHI::present(viewport, source)`: a non-null `source` is copied into the back buffer first and must be `Sampled` with the viewport's size and format (`rhi_validate_present_source`, shared by backends). `NullRHI` keeps a ring of `frames_in_flight` reusable slots: `present` clears the current slot, advances and completes the frame; `wait_idle` clears every slot and completes.
- `RHIViewportDesc` carries an opaque `void* native_window` plus pixel size and scale, never a window type; the caller fills it from `NativeWindowHandle`. Only buffers and textures take a creation-time debug `name` (`const char*`, not stored).

## Metal and Renderer (Step 4)

- The RHI owns resource mutation, as in Unreal: `IRHI::resize_viewport(viewport, w, h, scale)` replaces a viewport-side resize; `RHIViewport` is read-only (`width/height/format/acquire_back_buffer`).
- Frame pacing is a ring of `frames_in_flight` (3) frames owned by `MetalCommandQueue`; `end_frame` blocks with `waitUntilCompleted` on the oldest frame (polling, never a semaphore), and failures throw on the application thread. No semaphores, mutexes or completion handlers.
- A null `RHIViewportDesc::native_window` gives an offscreen viewport so the shared contract runs headless; a real window gets a child `NSView` hosting a `CAMetalLayer`.
- `Renderer` (static facade) owns the device, the clear colour and the per-frame `DrawItem` queue; `GraphicsLayer` owns the viewport and the frame (see Step 5).
- Manual check: `forge run -- --rhi=metal` (also with `MTL_DEBUG_LAYER=1`); `--rhi=null` draws nothing.

## RHI contract v2 and the Step 5 frame (Step 5)

- **Binding-layout model.** A pipeline is created with a binding layout (`bindings` + `binding_count` in `RHIGraphicsPipelineDesc`): an array of `RHIBindingDesc { kind, stage_mask, data_type, texture_dimension, slot, array_count, size }`. There are no names. `RHIBindingId` is an index into that table and is what every bind call takes (`bind_buffer`, `bind_texture(id, texture, array_index)`, `bind_sampler`, `set_constants(id, data, size)`). `RHICommandList` validates each call against the current pipeline's table (id in range, kind, constants size, array index, texture dimension, sampled usage, data type), so mistakes throw at record time, not in the driver.
- **Why the RHI does not reflect.** Reflection is a property of shader source, so it lives once, in `Shaders/` (`ShaderReflection`, `ShaderParameterMap`). `Shaders/ShaderBindings` turns it into the RHI layout (vertex and pixel merged, stage masks unioned); `Pipeline` keeps the name to `RHIBindingId` table. `RHIShader` holds only stage, entry point and code, so no second description can drift. In debug builds the Metal backend cross-checks the layout against Metal's own binding info and vertex attributes.
- **Constants and buffers.** `set_constants` copies up to 4096 bytes into the list arena and maps to `setVertexBytes`/`setFragmentBytes`, so per-batch camera data needs no uniform ring. `VertexBuffer`/`IndexBuffer` in `Dynamic` mode hold `frames_in_flight` regions in one CpuToGpu buffer; callers write `Renderer::frame_slot()`'s region and bind its `offset()`. The queue blocks on the oldest frame in `end_frame`, so an in-flight region is never overwritten.
- **`present` / `end_frame` split.** `IRHI::present(viewport, source)` only encodes and commits presentation. `IRHI::end_frame()` advances the frame ring and serial, once per frame, after `present` (or alone when nothing was presented). `Renderer::end_frame` does both, in that order.
- **Metal argument-table conventions.** Vertex streams bind at `METAL_VERTEX_STREAM_BASE + slot` (base 16) so they never collide with buffer bindings `0..15`. Each binding maps to a per-stage Metal index (`slot` plus `array_index` for texture arrays); an `array<texture2d<float>, N>` needs every element bound, so batches fill unused elements with a 1x1 white texture.
- **Who owns the frame.** `GraphicsLayer` (pushed last) owns the viewport and the clear colour and calls `Renderer::end_frame`; other layers never touch the pass. Layers hand the renderer data: `Renderer::submit(const DrawItem&)` queues one draw (pipeline, vertex/index buffers, inline constants, textures and sampler; the Unreal `FMeshBatch` analogue). `end_frame` acquires the back buffer, records `begin_pass`, `record_draw_item` for each item in order, `end_pass`, then `submit`, `present`, `end_frame`. `BatchRenderer2D` (Step 6) will batch into `DrawItem`s, and sorting by state or extra passes can be added inside `end_frame` without changing layers. Items submitted after `GraphicsLayer` ran land in the next frame.
- **Corrections (F8).** The Metal queue polls and retires finished frames and waits with `waitUntilCompleted`; it uses no semaphore or completion handlers, and the layer sets `framebufferOnly = false`.
- **Oasis front-end.** With graphics built in, `Oasis` opens a window and plays through `BoardLayer` + `PresentedGraphicsBoard2D` (Step 8b): queued `Renderer::draw_*` calls in a pixel-unit `Camera2D`, clicks hit-tested back to spaces through `BoardProjection2D` and turned into moves by `MoveBuilder`. `--rhi=null` runs the same path and draws nothing. `BoardLayer` restarts a finished game (`R` or a click after a short delay). The layout maths is unit-tested for any window size and assumes `NativeWindowHandle` width/height and `Input::cursor_position` share units (logical points). Still to verify by hand on a Retina display: click each cell's corners and centre and compare with the hover highlight, resize the window, then run once with the real Metal backend. Step 6/7 history below refers to the retired playground. Graphical Oasis also adds `OasisShell` (Interface phase: menu bar, side panel, confirm modal; it feeds the board region to `InputRouter::set_view`), and `GraphicsLayer` runs `FramePhase::Interface` clients before `World` ones while `SceneRenderer` orders sources by draw layer and gives each a region camera and clip; see [Dashboard](dashboard.md).

## Batching and the scene facade (Step 6)

- **Two layers, one rule.** `BatchRenderer` (base) accumulates transient primitives and turns each run of identical state into one `DrawItem` pushed to an injected `std::vector<DrawItem>&` sink, in submission order. `BatchRenderer2D` (derived) is only the primitive API: it registers one stream per `Primitive2D` from `primitive_traits()` and writes `Vertex2D*` vertices. Neither the base nor any batcher touches RHI commands; `GraphicsLayer` records the sink.
- **Streams.** A `BatchStreamDesc` (vertex size, vertices and indices per primitive, textured, `PipelineDef`) is one row; a derived class adds rows with `register_stream`, so a 3D or glyph batcher reuses all of the machinery. Indexed streams are quads (4 vertices, 6 indices) drawn from the shared static `DefaultResources::quad_indices` (U16, `QUAD_INDEX_MAX_QUADS` per draw); lines and triangles are non-indexed. A primitive is added as `select` (stream and sampler) then `acquire_texture` (textured streams) then `append`; only the first two can flush, so a slot index never goes stale.
- **State tracking and flush rules.** The batch key is `{stream, sampler}` (the pipeline follows from the stream; blend is baked into it). A change flushes the open batch with a counted `FlushReason`: `StreamChange`, `SamplerChange`, `TextureSlotsFull`, `IndexLimit` (the per-draw quad cap), plus `Explicit` (`flush`) and `End`. Only consecutive draws with identical state merge, so submission order is the batching contract; there is no sorting inside the batcher.
- **Storage.** Vertices are staged on the CPU per batch. A flush copies them into a `TransientAllocator` page (one persistently mapped upload buffer per page, one region per frame in flight; pages are 4 MiB, a larger request gets its own page, and pages persist, so a steady frame allocates nothing) and the `DrawItem` binds that buffer at a byte `vertex_offsets[0]`. Queued items keep the page alive. `recycle(frame_slot)` rewinds the pages; the owner calls it when a slot's frame begins (`record_frame` does it right after `end_frame`), never between scenes of one frame, so several scenes can share a frame.
- **Texture slots.** `TextureSlotTable` maps textures to slots in one batch: slot 0 is the white default, repeats reuse their slot, and a full table flushes. The count is `TextureArrayPermutations::value(permutation)`; `RHI_MAX_TEXTURE_BINDINGS` (32) is the compile-time ceiling shared by `DrawItem`, `TextureArrayPermutations` and the table, and the batcher picks the 32-slot permutation only when `RHICapabilities::max_texture_bindings` allows it, else 16.
- **Camera and constants.** `Camera` (projection and view `Mat4f`) is the only per-scene input, so 2D and 3D share `begin(const Camera&)`. Each draw carries `BatchConstants { view_projection }` (column-major) as inline constants.
- **Scene rules.** `SceneRenderer::begin_scene` inside a scene, `submit`/`end_scene` outside one, `draw_*` on a batcher outside its scene, and `end_frame` with a scene (or a batcher scene) still open throw `Error`. Coordinates are world units in a **left-handed** system (+x right, +y up, +z into the screen; `Mat4f` view space looks down +Z, `look_at`, `orthographic` and `perspective` follow it, clip depth is [0, 1]); a primitive's position is its centre and rotation is counter-clockwise radians about it; a sprite's uv rectangle runs from its top-left to its bottom-right corner.

### BatchRenderer and SceneRenderer: siblings, not a hierarchy

`SceneRenderer` (`Renderer/Scene/`) follows Unreal's split between dynamic primitives (`FSimpleElementCollector`, batched elements) and `FSceneRenderer` (views, passes, visibility, mesh batches); its design is under [Rendering architecture](#rendering-architecture-step-10-session-7).

| | `BatchRenderer` | `SceneRenderer` |
|---|---|---|
| Role | accumulator for dynamic, transient 2D/3D primitives (UI, gizmos, debug, procedural shapes) | owns the frame's batcher and pass list; runs every queued `RenderSource`'s stages in order; later sorting, culling and mesh batches; no mandatory scene graph |
| Input | `draw_*` calls between `begin(camera, target)` and `end()` | `begin_scene(RenderView)`, `submit(RenderSource&)`, `end_scene()` |
| Output | `DrawItem`s into the sink of the pass it was targeted at | the same sinks: one `RenderPass` item list per routed pass |

- **No inheritance.** `SceneRenderer` does not derive from `BatchRenderer`: it is not a kind of accumulator, and inheriting would drag primitive state into view/stage logic. **Composition instead:** it owns a `BatchRenderer2D` today and gains a `BatchRenderer3D` and sibling emitters (e.g. a `MeshRenderer`) as stages are added; all write `DrawItem`s that `record_frame` records.
- **One 2D path.** The static `Renderer::begin_scene/draw_*` forwarders were removed once `SceneRenderer` existed (Oasis never called them; only the board front end did). `scene().batcher_2d()` stays for direct use; `Renderer::submit(DrawItem)` and `StageContext::emit` are the direct-`DrawItem` paths.
- **Batcher lifetime.** The scene owns its batchers and recycles them in `finish_frame`; there is no `RendererContext::batchers` list. A list returns only when a second owner outside the scene needs recycling. A batcher takes its sink and pass formats per scene through `BatchTarget`, so one batcher serves any pass.
- **Seams Step 6 provides:** the sink is injected and the camera is a parameter; sorting and culling live outside the batcher; the camera base class carries 2D and 3D alike. Deferred until a consumer exists: a `DrawItem` sort key, instanced quads, a custom-pipeline hook on a stream (SDF text, materials), and a `draw_sprite(AssetHandle<ImageAsset>)` overload (the `Application` owns no `AssetManager` yet).

### Rendering architecture (Step 10, Session 7)

```text
Game ─IBoardPresenter─► BoardView (per seat: pieces + shared layout, no camera) ─BoardPresentation─► BoardScene (styles, highlights, drag; no camera)
                                                                                                         │
 GraphicsLayer: scene.begin_scene(RenderView{camera, logical, framebuffer, scale}) ─► clients submit RenderSources (boards, HUDs)
                                                                                                         │
 scene.end_scene(): for each stage, for each source: render_stage(stage, StageContext{view, pass, batcher_2d})
   Shadow ► Opaque3D ► Transparent3D ► Scene2D ► Overlay ► PostProcess      (content built: Scene2D, Overlay)
      │ routed to a RenderPass each (default: Opaque3D..Overlay → Main, the back buffer; Shadow, PostProcess unrouted)
      ▼
 record_frame: passes in stage order (consecutive stages sharing a pass = one RHI pass) ─► RHICommandList ─► Metal / Null
```

- **Name mapping (the brainstorm's terms versus the code).** "Scene" (what exists) is `BoardView` + `BoardScene`, both headless and camera-free; "view" (how it is seen) is `RenderView` (camera, logical size, framebuffer, scale) plus the front end's `BoardProjection2D`/`BoardTheme2D`. `BoardView` keeps its name because it is the per-seat observation every presenter, test and game uses; a camera never lives in it.
- **API.** `Renderer::scene()` returns the `SceneRenderer`; `begin_scene(view)` opens one scene, `submit(source)` queues a non-owning `RenderSource`, `end_scene()` runs the stages (and closes even when a stage throws), `render(view, source)` is begin + submit + end, `SceneScope` is the RAII form. `GraphicsLayer` opens one scene per frame around its clients and ends it before `Renderer::end_frame()`; a scene error there is logged and drops the clients, like a client error. Overlay draws nothing for a zero-sized view.
- **Collect, then run stages across sources.** Stages run stage-major (every source's Scene2D before any Overlay), so a board, a HUD and a debug overlay submitted by different clients still compose in pipeline order. Debug shapes replay at the end of Scene2D.
- **Engine-level types only.** `SceneRenderer` sits in `Renderer/`, below `Board/Graphics/`, so it takes a `RenderSource` (one virtual, `render_stage(RenderStage, StageContext&)`; ignore the stages you do not draw in), never a `BoardScene`: the engine learns no game, and a non-board or 3D application reuses it. `PresentedGraphicsBoard2D` is itself a `RenderSource` (board in Scene2D via `draw_board_2d`, the buttons and status line in Overlay, built by `run_board_overlay` with `oryx::ui` in `update` and replayed from the `UiContext`'s `DrawList`) and submits itself from `render`. A new stage is one enum entry, one loop iteration and a default no-op, so existing sources do not change.
- **Passes (an ordered list, not a graph).** A `RenderPass` is a `RenderPassDesc` (name, colour target or the back buffer, optional depth texture, load/store actions, clear values) plus the frame's `DrawItem`s. Pass 0, `Main`, is the back buffer. `add_pass`/`remove_pass`/`route_stage` configure the list; a pass must cover consecutive stages (checked), unrouted stages and empty passes are skipped, and Main always records so the frame clears. `record_frame` begins one RHI pass per run of stages sharing a pass (`RHIRenderPassDesc`, with debug groups named after the pass) and records its items with `record_draw_item`. `Renderer::submit(DrawItem)` appends to Main ahead of the scene's output; `StageContext::emit` appends to the stage's pass; a batcher flushes into it at stage end or on a state change.
- **Pass formats key pipelines.** `PassFormats { colour, depth }` is part of the pipeline key: `PipelineDef` carries `depth_test`/`depth_write`, `pipeline_desc(def, shaders, formats, permutation)` and `Renderer::pipeline(def, formats, permutation)` build for any pass, and `PipelineMemo` keeps one handle per format so passes do not evict each other.
- **3D readiness (seams, not built).** `RenderView::camera` is a plain `Camera`, so a perspective camera needs no new view type; 3D stages emit `DrawItem`s through `StageContext::emit` (no batcher is open in them); a depth attachment is a `RenderPassDesc::depth` plus `PassFormats::depth`; Shadow and PostProcess become live by adding a pass and routing the stage. Not built: `Camera3D`, `BatchRenderer3D`, mesh and material emitters, shadow and post content. The first 3D consumer adds those, a `RenderSource` and a pass, not new plumbing.
- **Direct RHI path.** Nothing here hides the RHI: `Renderer::rhi()`, `submit(DrawItem)`, `pipeline`/`resolve_pipeline`, `shaders`, the resource wrappers and a hand-built `RHICommandList` all work without a `SceneRenderer`, and a stage may mix `emit`, batched draws and `Renderer::submit`.
- **Batching is an optimisation.** A stage may call a batcher or emit `DrawItem`s directly; nothing forces a draw through `BatchRenderer`. Lighting, shadows and post-processing belong to the stages, not the batchers.
- **No scene graph, no frame graph.** A piece is placed by its space; passes run in stage order.
- **Data seam audit.** `BoardView` and `BoardScene` contain no camera, projection or transform (`Board/` outside `Board/Graphics` is blocked from `Renderer/` by the `headless !-> graphics` rule; the reverse, `Renderer/` including `Board/`, is true today (grep) but not a forge rule). Building a scene from an unchanged state allocates nothing once warm (`test_board_allocation`, `test_board_graphics_allocation`); `SceneRenderer`'s submit/end allocate nothing once warm (`test_scene_renderer`); `render` still makes under one allocation per frame inside the Renderer.

**What we borrowed, adapted and skipped**

| Source | Borrowed | Adapted | Skipped |
|---|---|---|---|
| Unreal | `FSceneRenderer` as the per-frame coordinator beside batched dynamic elements; `FRHICommandList` recording with a validation decorator (Step 10 Session 4) | stages are defaulted virtuals on a source, not a pass pipeline of mesh processors | `FScene` and primitive proxies, RDG (render dependency graph), parallel command lists |
| Unity / Godot | an error shader for failed shaders (`ErrorPS`); passes isolated from each other (one batcher scene per stage, one RHI pass per pass run) | a fixed C++ stage order instead of render pipeline assets or `RenderingServer` pipelines | SRP/URP asset pipelines, a retained scene tree |
| Bevy | camera as a separate view type next to the data (`RenderView`) | sorting left to a later pass over `DrawItem`s | ECS extraction, render phases and the render graph |
| Ludii / OpenSpiel | the observation is separate from rendering: a seat's view of a state is plain data (`BoardView`) | one presenter per game feeds the console and the window | game-specific renderers |

**When a frame graph becomes justified (record, do not build before).** The ordered pass list above covers linear frames. Move to dependency tracking only when any one of these appears: (1) a transient render target that two passes should alias, or that must be created and destroyed per frame by dependency; (2) a pass that consumes another's output where the order is not statically known (stages that would need to cover non-consecutive runs of one pass, or more than two passes with data-dependent edges); (3) compute passes with resource hazards that need barriers derived from usage; (4) user- or mod-defined post-processing chains; (5) per-frame pass culling whose cost exceeds the code that decides it.

## Presented boards (Step 8b)

A game library cannot afford a hand-written console board and graphics board per game, so presentation became data. The industry shapes this follows: model-view-presenter (the game stays the model; a stateless presenter describes it), a render list between presentation and rendering (Unreal's proxies, Bevy's extract step), and input as intents captured once per frame.

```
IState --IBoardPresenter::layout--> BoardLayout (static, shared)   --describe_pieces--> BoardContent (pieces + status, one seat's view)
       --BoardPresentation (change detection, last-move diff, MoveBuilder)--> BoardScene (layout by reference, styles, highlights)
BoardScene --board_text--> terminal          BoardScene --BoardProjection2D + draw_board_2d--> Renderer
picks (typed labels | clicks via space_at and the UI's option buttons) --MoveBuilder--> ActionId --poll_action--> SimulationLayer
```

- **Input.** `GraphicsLayer` owns the window and calls each registered `IFrameClient` once per frame, before it ends the frame, with a `FrameInfo` (input, logical and framebuffer size, scale, delta time). `IGraphicsBoard` is a frame client: its `frame()` builds one `BoardInput` (`read_board_input`: select, select_down, select_released, back, confirm, undo, restart, quit, cursor, viewport, scale), closes the application on quit and runs `update` then `render`. A restart input (the R key, or the board's own Play again button through `request_restart`; a click on the board no longer restarts) is held for `BoardLayer`, which takes it each frame (`IBoard::take_restart_request`) and restarts a finished game, so a restart reaches the simulation one frame after the click. Escape with the left button held is `back` (it cancels a drag) and otherwise `quit`. `BoardLayer` knows no window, device or renderer; the application passes it a `BoardFactory` that makes the windowed board and registers it with the `GraphicsLayer`. Boards never touch `Input` or the window, so they run in tests without one, and the key map and `k_restart_hint` live in one place. Picking is in logical points at every display scale.
- **Moves as picks.** A move is the sequence of picks a person makes: spaces, then optional menu options (promotion, which card). `MoveBuilder` holds the legal moves as a prefix tree of pick sequences (children in first-appearance order, built in one pass over the picks) and the picks so far as a path in it. `pick` returns a `PickResult`: `Rejected` (nothing changes), `Pending`, `Ready` or `Complete`. A move another move extends is legal and `Ready`: `confirm()` (a `Confirm` pick, offered as a button, Enter or the word "confirm") plays it, another pick continues, which is how a multi-jump can stop early. A pick that does not continue the path but begins another move starts again from it (clicking another piece re-selects). Equal sequences, an empty one or a `Confirm` pick in a candidate throw `Error`. `preview(pick)` lists what would follow a pick without taking it. `BoardInteraction` (headless) turns hover, press, release, option, confirm, back and undo into builder calls and holds the drag: a press on a pickable space picks it and, while the move stays open, starts a drag; a release over another space the move can continue to picks it, a release over the same space is a click and one anywhere else keeps the selection. Highlights, undo, back and drag are therefore written once for every game, and both front ends are thin over it.
- **Board units, not pixels; static layout, dynamic content.** The spaces of a board do not depend on the state, so they live in an immutable `BoardLayout` the presenter returns from `layout(state)` (a pointer change means a layout change; grid presenters return one memoized `shared_grid_layout`). `BoardLayout` is a concrete base, not an `I` interface, because every layout shares the same data: labels, tones, a label lookup, column and row labels, each space's **table position** (`Vec2f`; a 3D layout stores its top-down position, so the terminal and any generic front end work for every board), the distinct axes and the extent, all computed once in `finish()`, which also validates (labels non-empty, unique, no whitespace). It carries a `BoardDimension` tag (`Planar` or `Spatial`) and a virtual destructor, nothing else virtual. `BoardLayout2D` adds a `Vec2f` footprint and a `SpaceShape` per space (`add_space`, `finish`, `make_grid_layout`); a front end downcasts once per layout change with `layout_as<BoardLayout2D>()` (tag check plus `static_cast`, no RTTI; an `Error` when the game supplies another kind). Hit-testing is a free function per concrete layout: `space_at(const BoardLayout2D&, Vec2f)` (first match, inclusive edges). `BoardProjection2D` (screen fit: viewport, origin, scale) is the front end's own and is not part of the layout.
- **Presenter contract.** `describe_pieces(state, viewer, BoardContent&)` fills pieces and a status line for `viewer` (`out` arrives cleared): it must not reveal what `viewer` cannot see, and option-menu labels count. `BoardPresentation` passes the seat (single-seat) or the mover (hot-seat). Presenters are stateless: `layout`, `describe_pieces` and `action_picks` give identical results for any state sequence, repeated or reversed, and `layout` depends on the game, not on history (`test_registry_conformance.cpp`). A frame with an unchanged state allocates nothing in `BoardPresentation` or `PresentedGraphicsBoard2D::update` (asserted on a 19x19 fixture).
- **Styles name no technique.** `PieceStyle` carries a glyph, a colour and a `PieceShape` drawn from primitives. A 3D front end adds a model reference to it; sprites are deferred until a game ships images (`Board/Graphics/` may not include `Assets/`, so they would arrive as a `Texture2D` resolved by the application).
- **3D seam without a scene graph.** `BoardScene` is the render list: flat, holds the layout by reference plus a highlight vector, no hierarchy (a piece is placed by its space) and no camera or projection. A `BoardRenderer3D` would read the same scene with a `Camera3D`, meshes per piece kind and a depth pass, and emit `DrawItem`s; the engine-level `SceneRenderer` (above) stays unbuilt until that consumer exists, and would take over sorting and passes for it. Nothing in `Board/`, the presenters or the games changes for 3D.
- **Not yet:** move animation (the front end owns it, from `changed()` and the frame's `delta_time`), Python presenters, sprites and themes per game, undo that skips the opponent's reply (undo takes back one ply, as in the terminal).

## Resources and compiled assets (Step 7b)

- **Layout.** One resources folder per application holds the source assets and, beside them, the compiled output:

  ```
  Oasis/resources/
    fonts/ images/ shaders/ meshes/      sources, free-form; the importer is chosen by extension
    compiled/<type>/<hash16>.ox<type>    disposable and gitignored: .oximage .oxfont .oxatlas, later .oxshader .oxmesh
  ```

  `resources.root` (default `resources`, relative to the settings file, also when the key is absent) and `resources.compiled_enabled` live in `Core/ResourceSettings`; `assets.compiled_enabled` is ANDed with it and an empty `assets.roots` searches the resources root. There is no per-subsystem directory setting: every asset type shares `compiled/<type>/`.
- **Entry.** Header (magic, format version, importer version, 19-char type tag, key hash, length, payload checksum) then payload, written through a temp file and rename. Any mismatch, including a renamed or copied file, is a miss and the bad file is removed. The filename is the key hash only: the source path is outside the key (moved files still hit) and stays out of the bytes (determinism).
- **Types register themselves.** `OX_REGISTER_ASSET_IMPORTER` (and `OX_REGISTER_COMPILED_TYPE` for non-importer bakers such as the atlas) records the type's current version; `CompiledAssetStore::prune()` runs once per `AssetManager` and deletes entries of an unknown type, other format version, stale importer version, bad header, plus temp files. A new asset type (shader, mesh) gets its extension, header, prune and key by registering; the store does not change. Directory walkers (hot reload, a future cook) must skip `compiled/`.
- **Runtime, not cooked.** Entries are produced on demand at load. The key-addressed, self-describing format is the seam for a later offline `forge cook` that writes the same files.

### Deliberately not yet (Step 7b)

The compiled tree is disposable, so its format can change later for the price of a `FORMAT_VERSION` bump and a rebuild. What is costly to change is the user-facing source layout and settings (settled above) and the `IAssetImporter` signature (two importers). Each item below therefore waits for its first consumer, with the design noted so it is not re-derived:

- **Dependency graph.** First consumer is Step 9 (shader `#include`s). Build-time dependencies join the entry's key (the importer reports the included files and their bytes are hashed in); runtime references (a material naming a texture) are already possible because `instantiate` may load other assets, and the open part is reload propagation along them.
- **Per-asset `.meta` sidecars (import settings) and stable GUIDs.** The importer-wide `settings_hash` covers today's needs; GUIDs stay deferred with serialization (architecture §14).
- **Target-specific entries** (MSL now, Slang/SPIR-V later) are separate entries whose `settings_hash` includes the target, not a new layout.
- **Offline cook, shared derived-data store, processor/runtime split.** Deferred behind the key-addressed format above.
- **Eviction beyond staleness.** There is no LRU or size cap: a valid entry for a source that has changed stays until the folder is deleted.
- **Virtual paths** (`res://`-style mounts): the `assets.roots` list is the seam.

Comparison that shaped this (Unity `Library/`, Godot `.godot/imported`, Bevy `imported_assets`, Unreal `Saved/Cooked` and DerivedDataCache): one source tree, one disposable derived tree, type chosen by extension through an importer registry, derived entries keyed by content plus importer version plus import settings.

## Text and debug drawing (Step 7)

- **Font, not atlas.** `Font::create(make_font_source(assets, handle))` returns a move-only `Font` (the source is the only link to the asset system); `draw_text(position, utf8, font, TextStyle{pixel_height, colour, scale})` bakes the atlas for that height on first use and again after the asset reloads. A font that is not Ready draws nothing. Position is the baseline start of the first line, y up, so `\n` moves down by the baked line height.
- **Atlas.** R8 coverage sheet (shelf-packed, power-of-two, 1 px gutter) of Basic Latin and Latin-1 by default (`GlyphAtlasDesc::ranges`); pixels, glyph table and kerning are compiled through `CompiledAssetStore` (type `atlas`). Dynamic growth and SDF encoding are seams (`Vertex2DText::px_range`, `GlyphAtlasEncoding`).
- **Pipeline.** Text is its own stream and pipeline (alpha blend, same `TextureArrayPermutations` as `QuadPS`); switching between text and sprites flushes the batch.
- **DebugRenderer.** `Renderer::debug()` records line/rect/circle/text with a frame lifetime; the scene replays them at the end of its Scene2D stage under the view camera, and `record_frame` ages them.
- **Default font.** `Renderer::default_font()` is a `Font` over `BuiltinFontSource`: Inter (SIL OFL, licence in `Text/Builtin/`) embedded as a 16 KB subset (Basic Latin, Latin-1, U+FFFD; weight 450, no hinting or layout tables) and rasterised with stb_truetype on bake, so it is smooth at any pixel height. Always ready; no kerning. `DebugRenderer` uses it until `set_font` replaces it, so debug text needs no assets.
- **GUI path (Ui stream).** `replay` draws through `BatchRenderer2D::draw_ui_*` into one `Primitive2D::Ui` stream (`Vertex2DUi`, 28 B; `Ui.slang`): rects and lines on the white texel, glyphs (coverage or distance), square images, and rounded fills/borders as one signed-distance quad each, so GUI content never breaks a batch except for scissor, sampler or texture-slot changes. The board and debug path keep the Quad/Text/Line/Triangle streams.
- **Stats.** `BatchStats::triangles` and `texture_slots_used` feed the overlay.
- **Hot reload.** `Assets::reload(handle)` keeps the handle and old asset alive, swaps on `Assets::update()` and bumps the revision; `GpuAssetCache` and `Font` poll `(id, revision)` and rebuild lazily. The playground's `R` key reloads its font and PNG this way.
- **Playground overlay (retired in Step 8).** Was a second batcher scene with a pixel-unit `Camera2D` (positioned at half the viewport so the origin is bottom-left); `PresentedGraphicsBoard2D` reuses that camera convention.

## Built-in shader sources

Built-in shaders live in `Oryx/shaders/` (`Common.slang`, `Builtin/*.slang`) and are addressed by virtual path (`/Oryx/Builtin/Solid.slang`; an include `"Oryx/Common.slang"` is `/Oryx/Common.slang`). `OX_REGISTER_SHADER` names the virtual path. `IShaderSourceProvider` resolves it: `FileShaderSourceProvider` (the `/Oryx/` mount mapped to `shaders.root`, default the source tree in dev builds), `EmbeddedShaderSourceProvider` (bytes generated by `Oryx/tools/embed_shaders.py` into `build/generated/EmbeddedShaders.cpp`, regenerated on `forge configure` and not committed, and checked against the loose files by a unit test) and `LayeredShaderSourceProvider`.

`shaders.source_mode`: `auto` (loose files with a one-time warning per path that falls back to the embedded copy; Dist uses `cooked`), `file` (strict), `embedded`, `file_then_embedded`. `Renderer::reload_shaders()` recompiles from the configured sources and keeps the running shaders when a compile fails; includes are hashed through `ShaderCompilerInput::includes`, so an edited include invalidates every dependent shader.

## Compiled shaders

Compiled output is cached by `ShaderHash` (source, include closure from `IShaderCompiler::dependencies`, defines, entry, stage, target format, compiler id and version). `ShaderCache` looks in memory, then an optional `IShaderBinaryStore`, then the compiler; a store hit restores binary and reflection (`ShaderSerialisation`) without compiling, and failed compiles are never written. `Shaders/` only declares the store interface; `Assets/GpuShaderStore` implements it over `CompiledAssetStore` (`compiled/shader/<hash>.oxshader`, `compiled/shadermap/<id>.oxshadermap`) and `Renderer::init` receives it as `RendererDesc::shader_store`. Shaders never include Assets; the `Assets/Gpu*` bridges are the only Assets files allowed to include Shaders.

Cooking (`--cook-shaders`, `Assets/GpuShaderCook`, `Shaders/cook_shaders`) compiles every registered `ShaderType` permutation into the store and writes a `ShaderMap` (type name and permutation to `ShaderHash`, identified by a hash of the registered types, paths, entries and permutation defines). `shaders.source_mode: cooked` (the Auto mode of Dist) loads from the map with no sources and no compiler; a missing map, stale id or missing binary is an `Error`, never a silent compile. Dev modes keep compiling from source through the persistent cache.

Slang (Step 9) plugs in without format or API changes: its compiler implements `dependencies()` (`import`/`#include`), pins its `slangc` version as a constant so a cache hit never probes or needs the tool, sets `ShaderCompilerOutput::language`/`compiler_id`, and fills `ShaderReflection` directly. `ShaderBinaryFormat::MetalLib` is reserved in the persisted enum; emitting it (`xcrun metal`) and loading it in `MetalDevice` are follow-ups, as is a `forge cook-shaders` wrapper. A `ShaderAsset` and its Gpu bridge are a recorded seam, not a follow-up (see [ShaderAsset](#shaderasset-decision-and-seam)).

## Slang (Step 9)

Built-in shaders are `Oryx/shaders/Common.slang` and `Builtin/*.slang`. A shader file may hold any entry points and stages; each `ShaderType` names (file, entry, stage) and `SlangCompiler` runs `slangc -target metal -entry E -stage S` once per type, with `#include "Oryx/Common.slang"` resolved from the include map into a per-compile temp directory. Output is MSL source (`ShaderBinaryFormat::MslSource`, `compiler_id = oryx-slang`), so the Metal backend and the compiled-asset store are unchanged. Reflection comes from `-reflection-json` (parsed with yaml-cpp): only bindings the entry point uses are reported, a loose uniform is an `Error` (declare a `ConstantBuffer`), and an entry-point or stage mismatch is an `Error`. Matrices are column-major (`-matrix-layout-column-major`) so `mul(frame.view_projection, v)` matches the old MSL.

The tool path is `OX_SLANGC`, else `shaders.slangc` in the settings file (relative paths resolve against it, like `root`; a bare command name needs `./` or an absolute path), else the build-time `OX_SLANGC_PATH`, else `slangc` on `PATH`. The settings value reaches the compiler explicitly: `ShaderCache::set_slang_options({ settings.slangc })`, called by the renderer init and the shader cook, so there is no global state and `SlangCompiler::id()`/`version()` stay constants. It is only needed on a cache miss, never for a store hit or a cooked run. `SlangCompiler::version()` is bumped with the pin in `forge.toml`. After every graphics `forge compile` the Oryx plugin runs `Oasis --cook-shaders`, so a shader that fails to compile fails the build and the compiled store is warm. `MslShaderCompiler` stays in `Shaders/` for MSL sources (tests, application shaders).

### Runtime reflection cross-check

Offline reflection is the source of truth (as with Unreal's serialized shader parameter maps); the GPU object is only used to *validate* it, in development builds, at pipeline creation (the point where D3D12 checks input layouts and Unreal's Metal RHI reads pipeline reflection). A lone `MTLFunction` exposes only vertex attributes, and a fragment function cannot be reflected without a vertex partner, so no `RHIShaderReflection` exists. `MetalPipeline` runs the check in Debug and Release and compiles it out in Dist (`RHICapabilities::validates_shader_interface`):

- Per stage binding: kind, slot, constants size, texture array length, texture dimension and sampled scalar type.
- Per active vertex attribute: location and type against the vertex input (the Shaders layer already checked the vertex input against the compiler's reflection, so the check is transitive).

A mismatch throws `RHIInterfaceMismatch`; `make_graphics_pipeline` rethrows it as an `Error` naming the shader parameter and the vertex/pixel entry points. NullRHI has no shader code to reflect and skips the check; the shared `run_shader_interface_contract` asserts the throw only where `validates_shader_interface` is set. The check already caught `MslShaderCompiler` laying out `float3` as 12 bytes (MSL `sizeof(float3)` is 16). The built-in Slang pipelines are built on a real Metal device in the tests, which also confirms the unattributed `Texture2D textures[N]` parameter binds at the slot reflection reports.

### Board front-end seams (Step 10, Session 1)

Rationale trimmed from `Board/` and `Board/Graphics/` header comments:

- `BoardScene` is the seam between presentation and rendering: the terminal prints it, `Board/Graphics` draws it in 2D, and a 3D renderer would draw it as models. A front end chooses how board units reach the screen, so one `BoardView` serves the terminal, a 2D window and a 3D table.
- `PieceStyle` carries what each front end needs (`glyph`, `shape` and `colour`); a 3D front end adds a model there, and games never name a rendering technique.
- Presenters are registered per game name, like boards, so a game's rules never depend on how it is shown; they must be stateless because front ends may call them at any time and in any order.
- `GraphicsBoardFactory` is supplied by the application because the generic presented board draws, so it lives above the headless `Board/` module.
- A 3D presented front end would reuse everything in `PresentedGraphicsBoard2D` except the projection and `draw_board_2d`.

## ShaderAsset: decision and seam

A shader today is a **C++ class** (`QuadPS : BuiltinShader<PixelShader, TextureArrayPermutations>`) registered with `OX_REGISTER_SHADER(Class, "/Oryx/Builtin/Quad.slang", entry, stage)`. The class is the compile-time identity (`typeid`), permutation domain and `defines_for`/`should_compile` hooks; `ShaderLibrary` is keyed `(type_index, permutation)`, `library.get<QuadPS>(p)` is a typed `static_cast` and `PipelineDef::shaders` is a function pointer over those types. The **source is already external**: a virtual path resolved by `IShaderSourceProvider`, content-hashed, compiled, persisted, reflected and cross-checked by Metal at pipeline creation.

| | `StaticShader`/`BuiltinShader` (built) | `ShaderAsset` (hypothetical) |
|---|---|---|
| Identity | C++ type, compile time | `AssetHandle<ShaderAsset>` or path, run time |
| Entry, stage, permutations | C++ (`OX_REGISTER_SHADER`, domain type) | data (Slang `[shader("...")]` entries plus sidecar defines) |
| Parameter layout | C++ vertex struct and `SHADER_*_BINDING` names, checked at pipeline creation | discovered from reflection only; callers bind by name at run time |
| Lookup | `library.get<T>(p)`, typed | handle to a compiled `Shader`, untyped |
| Pipeline | `PipelineDef` function pointer to `library.get<VertexStage>()` | needs a handle-based `PipelineDef` (the deferred custom-pipeline hook on a stream) |
| Reload | explicit `Renderer::reload_shaders()` or F5 | `Assets::reload` bumps `revision`, consumers poll `(id, revision)` |
| Dependencies | provider hashes the include closure | same plus the asset graph (open since Step 7b) |
| Author | engine and application programmers | content authors: user, mod or material shaders |

External files, hot reload without resetting state, reflection and layout are already true of the built design, and `GpuAssetCache` yields textures, not shaders (shaders are deduplicated by `ShaderHash` in `ShaderCache` and persisted by `GpuShaderStore`). **Verdict: not built.** There is no consumer, a handle-based `PipelineDef` is itself undecided, and it would be a second way to name the same source. **Trigger:** the first application or material that needs a shader unknown at compile time. **Seam:** a `.slang` importer producing a CPU `ShaderAsset{source, entries, defines}`, `Assets/GpuShaderAsset` beside `GpuAssetCache` (the reverse edge is banned by the hard rule), a handle-based `PipelineDef`, and the include graph. Unreal's global shaders are C++ classes and its material shaders are data; Oryx has the global half.

## Shader reload and error fallback

- **F5 reload.** `GraphicsLayer::update` (compiled out in Dist) reads the key named by `graphics.reload_key` (default `F5`, an empty value disables it) and calls `Renderer::reload_shaders()`. A failure is logged by the layer (a layer may catch) and the running shaders stay: a reload that fails keeps the previous good shader, as in Unreal's `recompileshaders`.
- **Pink error shader.** Only the **pixel stage** falls back, and only on its **first** compile: when a registered `PixelShader` permutation fails and `shaders.error_fallback` is on, `ShaderLibrary` stores an instance of the same C++ class built from the embedded `ErrorPS` (solid magenta, no inputs, no resources, authored in MSL so it needs no `slangc`; `error_pixel_shader_input()`), logs the compiler diagnostics once with file and entry, and marks the pipeline `GraphicsPipeline::is_fallback()` so `bind_textures` does not throw for a draw item that has textures. The fallback is the same class because `library.get<T>` `static_cast`s; the `OX_REGISTER_SHADER` factory takes the entry from `output.reflection.entry_point`, not the baked name. A vertex-stage failure stays a hard `Error` (the fallback cannot know the stream's vertex layout).
- **Where it is on.** `shaders.error_fallback` defaults on in Debug and Release and off in Dist, cooked loads and the `Tests` binary, so CI still fails on a broken shader (and `forge compile` cooks every shader); a test compiles every built-in shader for real so a broken one cannot hide behind the fallback.

## Graphics settings (`graphics:`)

`GraphicsSettings` (`Renderer/GraphicsSettings.{h,cpp}`, `OX_REGISTER_SETTINGS(GraphicsSettings, "graphics")`, same pattern as `ShaderSettings`):

| Key | Default | Meaning |
|---|---|---|
| `vsync` | `true` | applied at viewport creation and live through `IRHI::set_viewport_vsync(RHIViewport*, bool)` |
| `max_fps` | `0` | optional frame cap, 0 or absent means uncapped; independent of vsync; paces to an absolute deadline (sleep to about 1 ms short of it, then yield-spin) and re-anchors when a frame runs late; `SettingsNode` has no float type so it is an integer |
| `idle_sleep_ms` | `50` | sleep used only when a frame presented nothing (minimised or occluded) |
| `reload_key` | `F5` | `F1`-`F12` or one letter; empty disables; ignored in Dist |

A negative or out-of-range value is a `SettingsError`. Settings are **reactive**: `on_settings_changed<T>(callback)` returns an RAII `SettingsSubscription`, and every load, reload, reset and `update_settings<T>(edit)` calls the subscribers (changed or not; a callback that throws is logged and the others still run). `GraphicsLayer` caches the section and re-applies it on notification, so `update()` does no settings lookup. Not added, no consumer: window mode, MSAA, backend (stays `--rhi`).

## Frame lifetime, window and device policy

- **Minimise and occlusion.** A hidden surface returns a null back buffer, so nothing renders and the loop would spin. `Renderer::end_frame()` and `record_frame` return whether anything was presented and `GraphicsLayer` sleeps `idle_sleep_ms` when not. The layer keeps no size of its own (the viewport owns it; `resize_viewport` stays for NullRHI), and a single `FrameInfo` is the size source for frame clients.
- **Window pumping contract.** `GraphicsLayer::update` pumps window events, so a layer disabled by an error stops pumping and the close button dies. Oasis exits non-zero on a disabled layer, so this is safe there; any other application must do the same.
- **Device loss is fail-fast.** A failed command buffer becomes an `Error` from `end_frame` carrying the frame serial and the open breadcrumbs; `LayerStack` disables the layer. Recreate-on-loss is a recorded seam (D3D12 `DEVICE_REMOVED` and Vulkan `ERROR_DEVICE_LOST` are handled the same way by Unreal and Godot). `NullRHI::fail_next_end_frame()` injects the fault in tests and a test proves shutdown stays clean afterwards. A failed `end_frame` skips the ring recycle, acceptable because the layer is then disabled.
- **Leaks.** At device teardown the exit report logs `RHIResource::live_report()` through `OX_CORE_ERROR` in every profile (Godot style) before the Debug-only assert. A Renderer teardown test asserts `live_count()` and `retired_pending()` are zero after repeated init, frame and shutdown cycles. `Renderer::init` registers its shutdown hook once.
- **`NullRHI` latency.** `NullRHIOptions{ simulate_latency }` (default on) retires resources and completes serials the way a GPU with frames in flight does, so a use-after-retire that Metal would expose fails on NullRHI too; the few tests that need immediate retirement construct it with `false`.
- **Screen scenes.** `SceneRenderer` runs each 2D stage as one batcher scene. `Camera2D::screen_space(width, height)` is the origin-bottom-left, y-up, logical-points camera the Overlay stage uses; `GraphicsLayer` opens the frame's scene (and never a GPU pass). `GraphicsLayer` stays the only owner of the frame, viewport, clear colour, present and window pump; boards never record or end a frame. `BoardTheme2D::font` (null means the default font) replaces the board's own font choice.
- **Capability fallback.** `RHICapabilities` plus clear `Error`s are the whole mechanism; the RHI has no MSAA or optional extension, so those cases are not applicable.
- **Known, not changed.** `present` encodes onto a second command buffer after `submit`'s (a possible later optimisation); `MetalDevice::upload_to_private` waits per upload (startup resources only; route per-frame uploads through `copy_buffer`); `MslShaderCompiler.cpp` (1,285 lines of MSL reflection parsing) is a size and maintenance candidate; the pipeline cache's 64-bit hash collision (about 2^-64) is accepted.
- **Verified by hand, not by tests:** the pink look, F5's visible effect, the CPU drop when minimised, Retina click accuracy and the vsync toggle (no screen capture here). Not covered: resize and reload storms, the shutdown-hook count and the destructor's log line.

## 3D seams

Carry over unchanged for a 3D board: `IBoardPresenter`, `BoardContent`, `BoardPresentation`, `MoveBuilder`, `BoardInteraction`, `BoardScene`, `BoardInput`, `BoardSession`, `BoardLayer`, the console front end and every game. The plug-in points (logged, not built):

- `BoardLayout3D : BoardLayout` (tag `Spatial`) adds `Vec3f` position, box footprint and orientation; its table position keeps the top-down `Vec2f`, so the terminal still works. `Vec3f` and `SpaceShape` stay in the codebase for it.
- `BoardProjection3D` is the camera (the 2D struct is the screen fit); `space_at_ray(const BoardLayout3D&, origin, dir)` is the picking function and must satisfy the same edge and tie-break tests as `space_at` (analytic, ray against the footprint, tie-break by index; no ID buffers or physics).
- `BoardScene` extent widens to `Vec3f` with the first 3D front end; `PieceStyle` gains a model reference with the Meshes work.
- `BoardRenderer3D`, `Camera3D` and a depth pass plug into `SceneRenderer` as new `RenderSource` stages (main 3D, with `BatchRenderer3D` or direct emitters); `PresentedGraphicsBoard3D` is a sibling of `...2D` sharing `BoardInteraction` and `read_board_input`.
- Smaller seams: a flip of the board in the projection (black at the bottom) and a `Hexagon` `SpaceShape` need only the layout, `space_at` and `draw_board_2d` to change.
- Hidden information: the presenter contract above is the whole mechanism today. Hot-seat flips the view to the next mover immediately, which would expose a previous mover's hidden hand on one screen; an interstitial is the logged seam, with the first hidden-information game as its trigger. Chance, simultaneous and hidden-information actions will need a richer decision type than an integer `ActionId`; `action_picks` and `PickResult` are the only board-side adapters to revisit.

## Adding a game

1. Game and state (`IGame`/`IState`), registered with `OX_REGISTER_GAME`; game ids stay below `PENDING_ACTION` (`is_game_action` is the "real move" test, `is_valid` only excludes `INVALID_ACTION`).
2. Presenter with `OX_REGISTER_BOARD_PRESENTER(Type, "game")`: `layout` (a cached, immutable `BoardLayout2D`, a grid via `shared_grid_layout` or `add_space` for anything else), `describe_pieces` (the viewer's view only), `action_picks` (distinct actions need distinct pick sequences; a sequence that is a prefix of another means "can stop here"; equal sequences throw), `piece_style`.
3. Labels are unique and whitespace-free (the console types them); a non-grid layout sets `text_grid()` false and the terminal lists spaces.
4. `test_registry_conformance.cpp` picks the presenter up by name: valid layouts, statelessness, picks that replay to exactly the legal actions.
5. Measure `legal_actions()`: past `k_action_list_inline_capacity` (9) every frame allocates; the trigger and fix are in the decision log. `ActionHistory` inline capacity (16) is the same kind of per-game number.
6. A hand-written `IConsoleBoard`/`IGraphicsBoard` stays the escape hatch for a game the scene cannot express; Python registers console boards, not presenters.
